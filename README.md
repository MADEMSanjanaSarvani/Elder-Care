# CareHive

**A person taking several long-term medicines has no accurate, current record
of what they actually take — not for themselves in the morning, not for the
doctor who asks, and not for the paramedic who can't.**

That is the whole problem CareHive solves. Everything in this repo either
serves it or is on its way out.

The app:

* rings on the phone at every dose time — exactly on the minute, offline, with
  a **Taken** button on the notification itself, so the dose is recorded at the
  moment the tablet is in your hand;
* keeps **taken**, **not taken** and **no record** as three separate facts and
  never merges them, because an unmarked dose is not evidence of a skipped one;
* puts the medicines, allergies, conditions and blood group on one **Medical
  ID** screen a paramedic can read off a locked phone;
* lets family see the same day, mark a dose themselves, and get the alert the
  moment SOS is pressed.

Nobody is dispatched, nothing is booked, nothing is charged. CareHive needs no
second party to work — which is exactly why it can work.

### What it used to be

Up to build 60 this was a caregiver marketplace: booking, matching, trips,
ratings, payouts, subscriptions, an AI companion. That product could not exist
without recruiting and paying caregivers, so it was removed rather than left
in as a set of buttons that go nowhere. Seventeen feature modules and a whole
second Flutter app were deleted; SOS, family access, check-ins and the
timeline were kept because they help family check on someone. The parts of
`docs/prd/` describing the marketplace are history now, not spec.

## Layout

```
docs/prd/                    the original three-part PRD (largely historical — see above)
supabase/                    schema, RLS, seed data, Edge Functions — see supabase/README.md
packages/setu_core/          shared Flutter package: models, consent logic, design tokens
apps/family_elder_app/       the CareHive app (family mode + elder mode)
apps/admin-dashboard/        internal ops console (Next.js — not Flutter; see its README for why)
melos.yaml                   Flutter monorepo tooling
```

Dart identifiers still read `Setu*` (`SetuColors`, `setu_core`). That is the
old codename surviving inside the code; every user-visible string says
CareHive. Renaming the symbols would be a large diff with no behaviour change,
so it hasn't been done.

## Why this structure

`setu_core` holds the consent-gating and design tokens so they can't fork
between the two experience modes. Every table that would otherwise hardcode
"India"/"₹" carries a `region_id` instead — though region no longer gates
anything in the app, since a medicine record works identically everywhere.

## Getting this running locally

Every piece of this repo has been built and validated with a real
toolchain at some point, not just written to spec — Flutter, Node, Deno,
Docker, and a local Postgres were all made available at various points
specifically to check that. **A real Supabase project is now live** —
project ref `veumfexjpxqhxemjaaor`, all 4 migrations/RLS/seed data applied
and all 13 Edge Functions deployed, with `regions-config` confirmed
working end-to-end via a real authenticated request. The two newest
functions (`me-data-export`, `me-erasure-request` — DPDP data-subject
rights) were validated locally (type-check, lint, and an extended RLS
smoke test) and then deployed manually the same way the first 11 were.
`.github/workflows/deploy-functions.yml` now also has a confirmed
successful run (`check` + `deploy` both green, 54s) — the first attempt
failed on a missing `supabase/config.toml` (never committed until that
was diagnosed), fixed and re-verified; the next push touching
`supabase/functions/**` will deploy automatically for real. See
`supabase/README.md`'s Status section for the full story, including
what the live milestone does and doesn't prove (short version: one
function is confirmed working live via a real HTTP call; the rest
deployed cleanly but aren't each individually verified yet, and no app
has been pointed at this project and run by a human).

- `flutter analyze`: clean across `packages/setu_core` and `apps/family_elder_app`; the app also fully compiles (`flutter build web`, a compilation check only — neither app ships to web) and have real Android platform folders committed (`apps/*/android/`, generated by `flutter create` against the existing `lib/`).
- `npm run build`, `tsc --noEmit`, `eslint`: clean on the admin dashboard.
- Database schema + RLS: applied to a real local Postgres 16 + PostGIS instance; an 18-case functional test suite (`supabase/tests/`) proves the consent model's core guarantees hold (plus the DPDP erasure-request queue's and caregiver payout accounts' own access rules), and caught one real bug along the way.
- Edge Functions: all 14 type-check and lint clean under Deno 2.9 (`deno check` / `deno lint`); the two pure-logic shared modules have real, passing unit tests. 13 of 14 are deployed to the live project — `payouts-run` (and its migration, `0005_caregiver_payout_accounts.sql`) exist in this repo but haven't been applied/deployed live yet — see `supabase/README.md`.

```bash
# Backend — schema/RLS validated locally AND live against a real project
cd supabase && supabase db reset && supabase functions serve   # needs the Supabase CLI
deno test --allow-net=api.openai.com functions/_shared/         # needs Deno — passes today

# Admin dashboard
cd apps/admin-dashboard && npm install && npm run build

# Each Flutter app — flutter pub get && flutter analyze both pass clean;
# `flutter run` still needs real --dart-define values (see each app's README)
cd apps/family_elder_app && flutter pub get && flutter analyze
```

**What's still missing, regardless of how clean the above sounds:** no
Flutter app has ever actually been opened in a browser/emulator/device by
a human and pointed at the live project — compiling and type-checking is
real signal, it isn't the same kind of confidence as watching the thing
run. On the backend side, 6 of 14 functions are now individually invoked
and verified over live HTTP (`regions-config`, and the full
`bookings-create` → `bookings-match` → `otp-start` → `otp-end` →
`sos-trigger` lifecycle, including payout scheduling and audit logging);
the remaining functions either deployed cleanly but haven't each been
exercised (`payouts-run` isn't deployed live at all yet), or are blocked
on third-party credentials nobody has configured yet (Razorpay, IDfy,
OpenAI) — see `supabase/README.md`'s Status section for exactly which.

## Deliberately not yet built

See `supabase/README.md` and each app's README for what's scoped out of
this pass — notably: the n8n schedule that would actually invoke
`payouts-run` on a timer (the function itself now exists), read-path
audit logging (every state-mutating Edge Function now writes to
`audit_log`, but nothing logs *reads* — Postgres has no native
SELECT-trigger auditing, so that needs per-repository instrumentation),
live caregiver GPS tracking, push notifications, and the full
10-language rollout. These were left as documented gaps rather than
filled with placeholder logic — check the
relevant PRD section before implementing them.
