Missing Modules, Batch 1: Family Experience

Part 4 of the Project Setu PRD, covering the first of seven batches across 25 modules requested beyond the MVP already specified in Parts 1–3. This batch is the tightly-coupled core of what a family member actually opens the app to do: see how their elder is doing (Dashboard), understand the full history (Timeline), get a daily wellbeing signal even on days with no booked visit (Daily Check-ins), and manage who else in the family has access (Family Member Management). Every design here extends the already-implemented booking, OTP, caregiver verification, SOS, payments, and DPDP modules — none of those are modified except where explicitly called out in § Touches to existing modules as narrowly-scoped, additive, necessary changes.

Batch overview

Why these four, together

Dashboard is the landing screen; Timeline is the data model that feeds its "recent activity" widget; Daily Check-ins is the single highest-value new *data source* Timeline needs to be worth building; Family Member Management is what makes "who sees this" — the question every other module in this batch has to answer — an actual product surface instead of a database table nobody can see or manage. Designing them together avoids four independent teams inventing four different answers to "how does consent-gated visibility render in the UI."

One consistent rule, used by all four modules below

A family member who lacks consent for a category never sees a blank space or a silently-missing widget — they see the category exists, with a "request access" affordance that notifies the elder. Hiding categories entirely would look like a bug; showing locked content in the clear would leak its existence without consent. This is decided once, here, and referenced rather than re-litigated in each module below.

Module 1 of 4

Family Dashboard

The landing screen for anyone signed in as family_member: one elder (or a switcher across several), one glance, consent-gated the same way every other read in this system is.

01Problem being solved

Family members — often overseas, often managing an elder alongside a job and their own household — currently have no single view of how their elder is doing. The booking screen shows bookings; the consent screen shows grants; nothing shows the composite picture a worried adult child actually wants at a glance. This is the single highest-frequency screen in the whole family-facing app, and today it doesn't exist as a distinct surface — PRD Part 3's "family-mode home" is a basic placeholder, not a real dashboard.

02User personas

Family member
Primary user. Default landing screen on sign-in.
full access, consent-gated per widget
Elder
Not a dashboard user — has their own elder-mode home (unchanged).
no access to this screen
Caregiver
Not applicable.
no access
Admin
Equivalent visibility already exists via the admin dashboard's booking/caregiver pages.
no new admin surface

03Functional requirements

  • Elder switcher for family members linked to more than one elder (e.g. both parents); last-viewed elder persisted as default.
  • Widgets, each independently consent-gated: next scheduled visit (always visible — booking metadata isn't consent-gated when the viewer is the requester); recent visit history, last 5 (visit_history); medication adherence snapshot (medication_list); live location, shown only during an active booking or an explicit elder-app share toggle (location_live); recent AI visit summaries (health_notes); billing summary (billing); consent status (always visible — a family member always sees their own grants); care-team card showing the assigned caregiver's name, photo, and trust tier, no phone number (protects caregiver privacy, matches existing no-direct-contact pattern).
  • Active SOS banner — always visible regardless of consent, life-safety overrides gating exactly as sos_events_select RLS already does.
  • All widget actions deep-link into existing screens (book, manage consent, message support) — the dashboard performs zero writes of its own.
  • Empty states: no elder linked yet → invite-elder CTA; link status pending → "waiting for [elder] to accept," no data rendered; zero bookings ever → "book your first visit" CTA.

04Non-functional requirements

  • Performance: cold-start render <1.5s p95 for the full widget set on a mid-tier Android device on 4G.
  • Reliability: degrades to cached last-known state offline; never shows a blank crash state for a transient network failure.
  • Scalability: read-only composition over already-indexed, already-scoped queries — no new write contention introduced anywhere.
  • Accessibility: WCAG 2.1 AA baseline (this is the family-facing surface; elder-mode has its own stricter bar under Module 11).
  • Compliance: zero new data paths outside the existing consent-gated RLS — see § Security below.

06Information architecture

Dashboard becomes the new root route for family_member. Children: Elder Switcher (modal sheet), and one deep-link target per widget into screens that already exist or are specified elsewhere in this batch (Timeline, Family Member Management) or in the existing MVP (bookings, consent, billing).

No required new tables — this module is a pure read composition over existing tables (bookings, elder_health_notes, elder_medications, elder_locations, payments, consent_grants, caregivers). One optional table, low priority:

08API design

No new Edge Function required for MVP. The client performs parallel direct Supabase queries per widget, each already RLS-scoped. An aggregation endpoint is explicitly not being specified here — inventing one before real usage shows the per-widget approach is too chatty would be exactly the "fake API" the brief warns against.

—no new endpoints
Deferred: a dashboard-summary read-aggregation Edge Function, only if Phase 2+ traffic shows per-widget round-trips are a real latency problem.

09Security design

No bypass of consent-gated RLS, ever

Every widget query goes through the same has_consent()-backed policies as everything else. No dashboard-specific fast path.

"Who else has access" needs an explicit, opt-in decision

A tempting widget — but today's family_links_select policy only lets a family member see their own link, not siblings'. Showing this list requires a new policy and an elder-controlled opt-in, specified fully under Module 4, not decided casually here as a dashboard feature.

Read-path audit logging — this is the highest-value place to close that gap

Every write-path Edge Function now logs to audit_log; reads still don't. A family member viewing consent-gated widgets is exactly the kind of access DPDP's transparency principle cares about. Recommend: Dashboard is the first screen instrumented with client-triggered read-audit logging, not deferred indefinitely.

10AI architecture

Not applicable directly — the AI-summary widget surfaces existing, already-guardrailed ai_interactions.output_text. No new model call originates here. Future "here's what to check on" proactive suggestions belong to the AI Recommendation Engine (Batch 4), explicitly deferred, not built as part of the dashboard.

11Accessibility requirements

WCAG 2.1 AA: scalable text to 200%, 4.5:1 contrast minimum, screen-reader labels on every widget card, status never conveyed by color alone (the SOS banner uses icon + text), full keyboard/switch-access navigation.

12Notification requirements

Dashboard itself sends nothing. It triggers exactly one notification type: a consent-access request to the elder when "request access" is tapped, delivered through the Family Notification Center (Batch 3).

13Edge cases

  • Elder revokes all consent while dashboard is open → next fetch returns empty for gated widgets, no crash, "request access" state renders.
  • Elder de-linked mid-session → same graceful empty-state handling, not an error screen.
  • Active in-progress booking → dashboard shows a distinct "visit in progress" live state, not lumped with "upcoming."
  • Family member's session expires mid-view → standard re-auth, no dashboard-specific handling needed.

14Admin dashboard requirements

None. Ops already has equivalent visibility via the existing caregiver/booking admin pages — deliberately not duplicating a second view of the same data for internal users.

15Flutter project structure

apps/family_elder_app/lib/features/dashboard/ — data/domain/presentation per the existing convention. Each widget card consumes its existing feature's Riverpod provider (bookings, consent, etc.) rather than one monolithic dashboard provider, so consent-gating logic stays co-located with the feature that owns it instead of being duplicated.

16Supabase requirements

No new tables required for MVP (optional dashboard_widget_prefs noted above). No new storage buckets, Edge Functions, or cron jobs. Zero new RLS policies for MVP scope.

17Future scalability

Read-only composition scales horizontally without changes. Widget system is data-source-agnostic by design so Phase 2+ can add new widget types (wearable vitals, once that integration exists) without touching the dashboard shell. i18n-ready from day one via the existing preferred_language field.

Module 2 of 4

Elder Care Timeline

One chronological, human-readable feed of everything that's happened for an elder — the data model the Dashboard's "recent activity" widget needs, and the first genuinely new table this batch requires.

01Problem being solved

Visits, health notes, medication changes, and SOS events already exist as separate rows in separate tables with no unified narrative. A family member piecing together "what's been happening" today has to check four screens. Worse: elder_medications only stores current state (active boolean) — a medication being stopped just flips a flag with no record of when or why. There is no point-in-time history anywhere in the current schema.

02User personas

Family member
Consent-gated per event category, same rule as Dashboard.
read, filtered
Elder
Full unfiltered view of their own history.
read, unfiltered
Caregiver
Contributes events implicitly via existing writes; no new caregiver-facing timeline screen.
no read access
Admin
Equivalent reconstruction already possible via audit_log + existing tables.
no new admin surface (MVP)

03Functional requirements

  • Chronological, infinite-scroll feed per elder, filterable by category.
  • Locked (consent-gated) categories render as section headers with a "request access" affordance — never silently hidden, never leaked in the clear (the batch-wide rule from § Overview).
  • Event types at launch: visit_scheduled, visit_started, visit_completed, medication_added, medication_stopped, health_note_added, sos_triggered, sos_resolved. Stored as free text with an application-level enum, not a Postgres enum — so later batches (Appointments, Care Plans, …) can add their own event types without a schema migration each time.
  • Each event carries a short, pre-generated human-readable summary line — generated at write time by the source Edge Function, not rendered dynamically from raw metadata, so the feed reads consistently regardless of which module wrote the event.

04Non-functional requirements

  • Append-only; indexed (elder_id, occurred_at desc) for pagination.
  • Writes are fire-and-forget relative to the primary transaction they accompany — a dropped timeline event is degraded UX, never a correctness bug, since the source-of-truth table (bookings, elder_medications, etc.) is unaffected.
  • Retention indefinite by default, subject to the same DPDP erasure workflow as everything else.

3
Locked categoryTap → same "request access" flow as Dashboard, not a separate implementation.

06Information architecture

One Timeline screen, two entry points (Dashboard for family, elder-mode home for the elder), sharing the same underlying provider and the same "locked category" widget as Dashboard — extracted into setu_core so the consent-request UX isn't implemented twice.

RLS mirrors the existing elder_health_notes/elder_locations shape exactly: is_elder_self() OR has_consent(category) OR is_admin() OR the assigned caregiver during an active booking that matches related_booking_id — zero new security primitives, all existing helper functions from 0002_rls.sql reused as-is.

08API design

No new endpoint for reading (RLS-guarded direct query). No new endpoint for writing either — this is the one place in this batch where existing Edge Functions get touched, and it's covered fully under § Touches to existing modules: bookings-match, otp-start, otp-end, sos-trigger, and ai-visit-summary each gain one additive insert into elder_timeline_events call alongside their existing writes.

09Security design

Reuses has_consent() — no new access logic

The single riskiest thing a new table like this could do is invent its own authorization rule. It doesn't; it reuses the exact function every other consent-gated table already calls.

Timeline is where read-audit logging becomes a requirement, not a deferral

A family member scrolling an elder's full history is the single highest-value place to close the platform-wide read-audit gap. Recommend building this module with client-triggered audit_log writes on render from day one, rather than adding it later as a retrofit.

10AI architecture

Not applicable directly. Timeline surfaces existing AI-generated content (already guardrailed at the point of generation); it does not generate anything new. Could become an input signal for the AI Recommendation Engine (Batch 4) later — noted, not built here.

11Accessibility requirements

Same WCAG 2.1 AA baseline as Dashboard for the family view. For the elder's own view specifically: larger text and an optional single-category-at-a-time mode, consistent with the Accessibility Module (Batch 5) rather than reinventing an elder-specific UI kit here.

12Notification requirements

None — Timeline is passive and generates no notifications of its own.

13Edge cases

  • Brand-new elder, zero history → empty state, not an error.
  • Caregiver's booking-scoped visibility window closes (booking completed) → their access to that booking's entries persists (needed for dispute resolution), but does not extend to entries outside it — matches the existing elder_health_notes_select shape exactly.
  • Fire-and-forget insert silently fails → Phase 2+ hardening: a background reconciliation job that can rebuild missing entries from source tables, since those remain intact regardless. Not MVP-blocking.

14Admin dashboard requirements

None for MVP. A future "elder activity view" for support case investigation is a plausible Phase 2+ superset of the existing audit log viewer — deferred, not specified further here.

15Flutter project structure

apps/family_elder_app/lib/features/timeline/ — TimelineEvent domain model, paginated repository, TimelineScreen, CategoryFilterChips, and a shared LockedCategoryCard widget pulled into setu_core so Dashboard and Timeline don't each build their own version of the same locked-content pattern.

16Supabase requirements

One new table (elder_timeline_events) with its RLS policies. No new storage, no new scheduled Edge Functions. Five existing Edge Functions gain one additive insert call each — see § Touches to existing modules.

17Future scalability

Unbounded per-elder growth — plan partitioning or cold-storage archival once per-elder event counts get large (a Phase 3+ concern). The text-based event_type is deliberately not a rigid Postgres enum specifically so the other 23 modules in this plan can log their own timeline-worthy events later without schema churn.

Module 3 of 4

Daily Check-ins System

A one-tap daily wellbeing signal from the elder, for the days — most days — with no booked visit to otherwise confirm anything.

01Problem being solved

A booked visit confirms wellbeing on the days it happens; most days have no visit. Family currently has no lightweight, low-effort way to know the elder is okay in between. The gap this closes is specifically the silent day, not an emergency — which is exactly why this must not be built as, or confused with, a second SOS path.

02User personas

Elder
Primary actor — performs the check-in.
write own, read own
Family member
Receives status + missed-check-in alerts.
read, consent-gated
Caregiver
Not involved — visit-scoped signals are already covered by otp-start/otp-end/ai-visit-summary.
no access
Admin
Ops visibility into sweep-job health and a manual wellness-check override.
limited, scope TBD — see § Admin

03Functional requirements

  • Elder-mode home gains a fourth large-touch-target action: "I'm okay" (extends the existing three-action home screen from Part 3 — additive, no change to Call for Help / Book Help / Today's Visit).
  • Optional short mood field: small fixed vocabulary, not freeform text — deliberately, so nothing resembling a health claim gets captured as "mood" (see § Security).
  • Configurable per-elder expected check-in time and timezone; a family member or the elder can adjust it.
  • A completed booking on a given day auto-satisfies that day's check-in — otp-start/otp-end already proves the elder is fine; a redundant nudge on top of a real visit would just train family to ignore the feature.
  • Pause window for travel or a hospital stay (paused_until date) — should auto-suggest itself when an active Hospital Companion Services booking exists (Batch 3), cross-referenced not built twice.
  • Missed check-in → gentle nudge to the elder first, then escalate to family only if the elder also doesn't respond within a further window. Escalation is a "haven't heard from them today" notification, never an automated SOS trigger — SOS stays human/elder-initiated and 108-first-gated per the existing locked decision, full stop.
  • Any family member can mark a missed-check-in alert "handled" (e.g. "I called, they're fine"), which suppresses further escalation for that day for all linked family — avoids duplicate anxiety-inducing alerts to siblings who all get the same notification.

04Non-functional requirements

  • Notification delivery reliability is the load-bearing requirement here — a missed-alert that doesn't arrive defeats the feature. Depends on the Family Notification Center (Batch 3) meeting a real delivery SLA.
  • Must function for low digital literacy: single button, large target, works without navigating away from the home screen.
  • Sweep job (§ API) must scale across timezones without a rewrite — see § Future scalability.

05User flow

1

2
Elder misses the windowReceives one gentle in-app nudge before any family notification fires.
3
FamilyReceives "haven't heard from [elder] today" push/SMS at cutoff → taps "call now" or "mark as handled."
4
Admin(if a care-ops scope exists) sees sweep-job health and can manually trigger a wellness-check call for a flagged elder.

06Information architecture

Check-in button lives on the existing elder-mode home (additive). Status + history surface on Family Dashboard (Module 1) as a widget, and in full in Timeline (Module 2) as event_type = daily_checkin. A lightweight schedule-settings screen under family/elder settings.

New consent category: wellbeing_checkins

Check-ins are conceptually distinct from visit history — an elder might reasonably share daily wellbeing broadly while keeping detailed visit/health history more restricted, or the reverse. This needs one additive value on the existing consent_category enum (alter type consent_category add value 'wellbeing_checkins') — a minimal, backward-compatible, and genuinely necessary touch to the existing consent model, flagged in full under § Touches to existing modules.

08API design

—check-in write
No Edge Function — plain RLS-guarded insert, no secret, no cross-table rule.
POST/checkins/escalation-sweep
New scheduled Edge Function, triggered externally (n8n/cron — same pattern as payouts-run). Sweeps all elders past their expected_by_time with no check-in and no active pause, writes checkin_escalations, fans out notifications. A genuine batch job, not a per-request operation, so it earns its own endpoint unlike the write path above.

09Security design

Mood/note fields are explicitly not health data

mood is a fixed vocabulary, not freeform. note is short and, if a future feature ever summarizes it via AI, must reuse the existing two-layer guardrail (_shared/aiGuardrail.ts) — never a new, unguarded AI path. Stated explicitly because "just a quick note field" is exactly the kind of surface that quietly grows into an ungoverned health-data channel if this isn't decided up front.

Escalation is never SOS

Restated for emphasis: a missed check-in triggers a family notification, never sos-trigger, never the 108-first flow. Conflating "haven't heard from them" with "emergency" would be a serious trust/safety regression, not a convenience.

10AI architecture

Not required for MVP (button + optional short note, no generation). Voice-initiated check-in (Batch 4) is the only AI-adjacent surface — speech-to-intent, not diagnostic, not summarizing content.

11Accessibility requirements

The clearest accessibility case study in this whole batch: one tap, no reading required beyond an icon + short label, large touch target for tremor/motor impairment, voice alternative. Baseline defined fully in the Accessibility Module (Batch 5), applied here rather than reinvented.

12Notification requirements

Gentle in-app nudge to the elder before any family escalation. Missed-check-in alert to family via push + SMS fallback. "Handled" confirmation suppresses further alerts for that day across all linked family.

13Edge cases

  • Elder in hospital → paused_until covers it; should auto-suggest from an active Hospital Companion Services booking rather than requiring family to remember.
  • Elder's phone is dead/inaccessible that day → this is precisely the scenario the feature exists to catch; a booking existing that day does not suppress the alert unless that booking actually completed (see FR above).
  • Multiple family members, one marks "handled" → all others' pending alerts for that day are suppressed too.
  • Elder wants zero check-ins ever → schedule can be effectively disabled via a permanent pause; this is a real product/consent question (does disabling require family agreement?) flagged as needing a product decision, not decided unilaterally here.

14Admin dashboard requirements

Ops visibility into sweep-job health (last run, failure count) and a manual override to trigger a wellness-check call for a specific elder. Whether this needs a new, narrower care_ops admin scope or reuses sos_operator-adjacent access is an open decision for whoever prioritizes this — flagged, not pre-decided.

15Flutter project structure

apps/family_elder_app/lib/features/checkins/ — CheckInButton (elder-mode home, additive), CheckInHistoryWidget (feeds Dashboard), CheckInScheduleSettings.

16Supabase requirements

Three new tables (daily_checkins, checkin_schedules, checkin_escalations) with RLS mirroring existing elder-data patterns. One additive enum value on consent_category. One new scheduled Edge Function (checkins-escalation-sweep), externally triggered.

17Future scalability

The sweep job must batch efficiently by timezone from day one — Vizag-only MVP is single-timezone, but designing the query to group by timezone now avoids a rewrite at Phase 2+ multi-region rollout. Cadence is currently a single daily slot; multiple-times-per-day for higher-acuity elders is a plausible later extension, noted as a known future migration, not built now.

Module 4 of 4

Family Member Management

The missing UI and light role concept on top of family_links, which today is a bare invite/accept/revoke table with no interface at all.

01Problem being solved

family_links (PRD Part 2 §11) already has the right lifecycle in the schema — but no screen exists to invite, view, or manage family members through it, and there's no way to differentiate "the sibling who coordinates scheduling" from "the sibling who just wants to be kept informed" beyond per-category consent, which answers what someone can see, not who's the first point of contact.

02User personas

Family member
Invites others, manages own settings, can self-revoke.
full, scoped to self
Elder
Sovereign viewer — sees the full access list, can revoke anyone.
full oversight
Admin
Guardian-process override already exists in consent_grants.granted_via (Part 2) — cross-referenced, not rebuilt.
existing path only

03Functional requirements

  • Invite by phone/email; invitee doesn't need the app installed to accept — a lightweight web accept flow reduces friction for low-app-adoption relatives, though full access still requires the app.
  • Coordinator flag (additive, see § Database): at most one primary coordinator per elder — a UX/notification-priority concept only. Coordinator status grants zero additional data access. This distinction is restated three times in this module because it is the single most likely place a future implementer conflates "coordinator" with "has more permissions."
  • Revoke rules: a family member may revoke themself; the elder may revoke anyone; one family member may never unilaterally revoke another's access — that would be a real abuse vector (a controlling sibling locking out a concerned one) and must be blocked at the RLS level, not just the UI.
  • "Who has access" list — primarily an elder-facing screen (elder is sovereign over their own data by design). Sharing that same list with other family members is an elder-controlled opt-in, off by default (resolves the open question flagged in Module 1).

04Non-functional requirements

  • Invite flow must work over low bandwidth / SMS-only reachability — no app-only path for the invite itself.
  • Rate-limited invites per elder to prevent spam-inviting strangers.

05User flow

1
FamilySettings → "Family & Access" → Invite → phone/email → sent.
2
InviteeReceives SMS/link → accepts (web or app) → appears as pending → active once app onboarding completes.
3
ElderSettings → "Who has access" → full list, per-member consent summary, revoke action.
4
AdminGuardian-process override for consent — existing PRD Part 2 workflow, unchanged.

06Information architecture

New "Family & Access" section under settings, in both elder-mode and family-mode. Invite screen, pending-invites list, active-members list with a deep-link into the existing consent management screen per member — not a duplicate of it.

08API design

POST/family/invite
New Edge Function — creates the pending family_links row and sends the SMS/email invite. Needs a secret-holding SMS/email provider, so it can't be a raw client insert, same "Edge Functions own anything touching a secret" rule as everywhere else. Also owns rate-limiting.

Accept, revoke, and coordinator-transfer stay as direct RLS-guarded writes against family_links — no secret, no cross-table rule beyond what RLS already expresses.

09Security design

Coordinator ≠ access. Restated once more.

The coordinator flag must never be read by any RLS policy or consent check. It is a display/notification-ordering hint, full stop.

Revoke policy, precisely

family_links_update must allow family_user_id = auth.uid() (self-revoke) or is_elder_self(elder_id) (elder revokes anyone) or is_admin() — and explicitly nothing else. No peer-to-peer revoke path, ever.

Revoking a link already revokes consent — no new logic needed

is_linked_family() already checks status = 'active', so every consent-gated query already loses access the moment a link is revoked. Confirmed here rather than rebuilt.

10AI architecture

Not applicable.

11Accessibility requirements

The elder's "who has access" list must be scannable at a glance for low digital literacy: avatar, name, relationship, one-line consent summary — not a dense table.

12Notification requirements

Invite sent / accepted / declined. Coordinator changed (to all linked family — transparency when the point of contact shifts). Revoked (to the removed member — a silent loss of access is a bad and confusing experience).

13Edge cases

  • The family member being revoked is also the one paying for bookings → their billing consent is already revoked automatically the moment the link is (see § Security), no special handling required.
  • Last remaining family member self-revokes, leaving the elder with zero oversight → allowed, with a strong confirmation warning and a notification to the elder — flagged as needing an actual product/legal opinion on whether this should ever be blocked, not decided unilaterally here.
  • Two family members simultaneously claim "coordinator" → prevented at the database level by the partial unique index.

14Admin dashboard requirements

None new for MVP — family_links is already queryable by ops if a support case needs it; the existing guardian-override consent workflow (Part 2) is the closest analog and isn't duplicated here.

15Flutter project structure

apps/family_elder_app/lib/features/family_access/ — InviteScreen, PendingInvitesList, FamilyMembersList (elder and family variants sharing a base widget), CoordinatorBadge.

16Supabase requirements

Two additive columns (family_links.coordinator, elder_profiles.share_family_list), one partial unique index, one new opt-in RLS policy for the transparency view, one new Edge Function (family-invite). No new tables, no new storage.

17Future scalability

Coordinator is a boolean, not an enum, deliberately — keeps MVP simple while leaving room to widen to a primary/secondary tier later without breaking existing data. SMS invite delivery should eventually route through a per-region provider (mirroring the existing regions.payment_provider abstraction) once multi-country rollout needs more than one SMS vendor — deferred to Phase 2+, not built now.
