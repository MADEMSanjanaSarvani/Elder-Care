Missing Modules, Batch 2: Care Logistics

Part 5 of the Project Setu PRD, second of seven batches across 25 modules. This batch covers the recurring, day-to-day logistics of managing an elder's care: what medications they're on and whether doses are being taken, when supply is running low, what external appointments are coming up, and — the one genuine architectural finding of this batch — a single shared reminder engine instead of three separate ones. Existing implemented modules (booking, OTP, caregiver verification, SOS, payments, DPDP) remain untouched except where flagged in § Touches to existing modules.

Batch overview

One finding worth stating up front

Medicine Management, Medicine Refill Management, and Appointment Management each independently need to remind someone about something at a scheduled time. Designing them one at a time would produce three near-identical scheduled sweep jobs, three notification-delivery code paths, and three slightly different ideas of what a "reminder" is. Designing them together surfaced that duplication early — so Smart Reminder System exists as the fourth module in this batch specifically to be the single shared engine the other three plug into, rather than a fourth independent feature competing for the same job. Each of the first three modules' API Design sections below states plainly which parts of the "remind someone" problem they still own directly (domain-specific generation) and which parts they hand off to Smart Reminder System (generic delivery).

Medicine Pickup already exists as a bookable service

service_catalog already has a medicine_pickup entry (non-clinical, ₹149, probationary trust tier — see supabase/seed.sql). Medicine Refill Management's job is connecting "you're running low" to booking that existing service, not building pharmacy logistics from scratch.

Module 5 of 4 in this batch (5th overall)

Medicine Management

The existing elder_medications table (0001_schema.sql) has no UI, no adherence tracking, and no history of dosage changes beyond a current-state active flag. This module builds the workflow layer and the one genuinely missing table: concrete, trackable dose instances.

01Problem being solved

elder_medications answers "what is the elder currently prescribed." It cannot answer "did they take this morning's dose" — there is no row anywhere that represents a single, concrete, time-boxed dose. Family cannot see adherence; nothing feeds a missed-dose signal to anyone.

Caregiver — clinical
Marks a dose "administered" only during an in-progress clinical booking.
booking-scoped, clinical only

booking-scoped, reminder only
Admin

03Functional requirements

  • CRUD on elder_medications (existing table, now with a real screen) — add, edit, discontinue.
  • Discontinuing a medication sets active = false and writes an elder_timeline_events row (medication_stopped, already planned in Batch 1) and cancels any pending future doses (see § Edge cases).
  • New rolling-window dose generation: turns a medication's schedule jsonb into concrete dose instances a few days ahead.
  • Dose marking: taken / missed / skipped, by elder (self), family (proxy — important for lower digital literacy elders), or a clinical caregiver during an in-progress booking.
  • Non-clinical caregivers may only log "reminded," never "administered." Administering medication is a clinical action; letting a companion/home-service caregiver mark a dose as taken would misrepresent who actually delivered care.
  • Editing dosage/schedule while a clinical caregiver is actively assigned should prompt re-confirmation — a family member silently changing a dose a nurse is mid-visit administering is a real safety gap worth naming explicitly, not just an edge case.

04Non-functional requirements

  • Dose generation must be idempotent — regenerating the rolling window must never create duplicate rows for the same medication/time.
  • Timezone handling shares the same per-elder timezone concept established for Daily Check-ins (Batch 1) — not a second, inconsistent implementation.

06Information architecture

Medication list screen (add/edit), a dose checklist/calendar view, refill status shown inline (see Module 6 — deliberately the same screen, not a fragmented second section).

RLS reuses the existing elder_medications shape (is_elder_self, has_consent('medication_list'), is_admin) plus one addition: a caregiver may write a row with marked_via = 'caregiver_clinical' only if is_assigned_caregiver(related_booking_id) holds, the booking is in_progress, and the caregiver's caregiver_type = 'clinical' — enforced in the policy itself, not just hidden in the UI, since a non-clinical caregiver attempting to mark "administered" must fail at the database, not just be prevented by a button that isn't shown.

08API design

POST/medications/generate-doses
New scheduled Edge Function (nightly, n8n-triggered). Domain-specific: turns schedule jsonb into concrete medication_doses rows for the rolling window. Also enqueues a corresponding row into Smart Reminder System's shared reminders table (Module 8) — generation and delivery are deliberately separate concerns, not duplicated logic.
—dose marking
Plain RLS-guarded update — no secret, no cross-table rule beyond what's expressed in the policy above.

09Security design

Clinical-only administration is an RLS rule, not a UI convention

Restated because it's the one place in this module where getting the enforcement layer wrong would misrepresent who actually delivered a medical action — the exact kind of gap that matters for both safety and legal accountability.

No new consent category

Doses inherit medication_list — a dose is exactly as sensitive as the medication it belongs to; inventing a second category here would be unnecessary sprawl.

10AI architecture

Not required. administered_note is short, human-authored, and — if ever summarized by AI in a future module — must go through the existing two-layer guardrail, never a new unguarded path.

11Accessibility requirements

Elder-mode dose marking reuses the same large-tap-target pattern as Daily Check-ins (Batch 1) — not a form, a single confirm action per due dose.

12Notification requirements

Owned by Smart Reminder System (Module 8) — this module only enqueues, never delivers.

13Edge cases

  • Medication discontinued with pending future doses → those transition to cancelled, not deleted, preserving the audit trail.
  • Non-clinical caregiver attempts to mark "administered" → blocked at RLS (see § Security), not just UI.
  • Dose taken early or late → scheduled_at stays fixed; taken_at records reality separately.
  • As-needed (PRN) medications with no fixed schedule → the calendar/checklist model doesn't fit; needs a manual "logged a dose" quick-action instead — flagged for whoever scopes the detailed UI, not solved by the default schedule-based flow.

14Admin dashboard requirements

None new for MVP.

15Flutter project structure

apps/family_elder_app/lib/features/medications/ — MedicationListScreen, DoseChecklistWidget, AddEditMedicationForm. apps/caregiver_app gets one additive, booking-scoped action ("Mark administered"), visible only for in-progress clinical bookings.

16Supabase requirements

One new table (medication_doses) with RLS extending the existing elder_medications pattern. One new scheduled Edge Function (medications-generate-doses). No new storage, no new consent category.

17Future scalability

The generation sweep should share a common timezone-batching approach with Daily Check-ins' sweep and, later, Appointment Management's recurrence expansion — worth extracting a shared _shared/scheduledSweep.ts helper once a third instance of this pattern exists, rather than three copies of the same batching logic. Noted as a real DRY opportunity for implementation time, not built now.

Module 6 of 4 in this batch (6th overall)

Medicine Refill Management

Connects "you're running low" to the medicine_pickup service that already exists in the catalog — this module is thin by design.

01Problem being solved

Medications run out; family need advance warning and a fast path to reorder. The platform already has a bookable pickup service — this module's entire job is the stock-tracking and the nudge, not pharmacy logistics.

02User personas

Family member
Sets stock/threshold, receives low-stock alerts, books the pickup.
primary actor
Elder
Read visibility, same consent gate as medications.
read
Caregiver
Can flag low stock observed during a visit.
booking-scoped write
Admin
None new.
none

03Functional requirements

  • Per-medication stock: quantity on hand, unit, refill threshold.
  • Auto-decrement on every dose marked taken in Module 5 — a database trigger, not application code in three different client paths (see § Database).
  • Threshold crossed → notification (via Module 8) + a "Book Medicine Pickup" CTA that deep-links into the existing bookings-create flow with service_id pre-filled to medicine_pickup and a note listing which medications are low.
  • Manual "mark restocked" resets the count.
  • No autonomous purchasing, ever. The system suggests; a human always taps to actually book. Stock estimates are advisory, and family can override them at any time.

04Non-functional requirements

Stock math must degrade gracefully — a wrong estimate should produce an early-but-harmless alert, never a false "you're fine" that causes a real gap in medication.

05User flow

1
FamilySets initial quantity + threshold when adding a medication.
2
SystemDecrements automatically as doses are marked taken.
3
Threshold crossedNotification fires; family taps "Book Medicine Pickup," prefilled.
4
Existing booking flowRuns unmodified from that point — bookings-create → bookings-match → OTP visit, exactly as it does today.

06Information architecture

Refill status is shown inline on the Medicine Management list screen (Module 5) — a deliberate choice not to fragment "medications" into two disconnected app sections.

07Database design

medication_stockone row per medicationnew
medication_iduuid fk, unique→ elder_medications
quantity_on_hand, unitnumeric / textunit from a small fixed vocabulary (tablets, ml, …), not freeform
refill_threshold, last_restocked_atnumeric / timestamptz—

RLS is identical in shape to elder_medications, reusing the same medication_list consent category — no new category needed.

08API design

—no new endpoint
Stock decrement is a Postgres trigger on medication_doses reaching status = 'taken' — the right tool here, since it stays correct regardless of which of the three marking paths (elder, family, caregiver) triggered it, rather than duplicating decrement logic three times in application code.

09Security design

No new sensitive data beyond what medication_list consent already gates.

10AI architecture

Not applicable.

11Accessibility requirements

Same baseline as Module 5 — inline status uses a simple, non-alarming visual (a stock-level indicator, not a stark red warning) consistent with the platform's tone discipline for non-emergency signals.

12Notification requirements

Owned by Smart Reminder System (Module 8).

13Edge cases

  • As-needed (PRN) medications don't auto-decrement via the dose-taken trigger (see Module 5 §13) — refill tracking for these needs a manual "logged a dose" entry point, same caveat carried over.
  • Threshold set to an unrealistic value (e.g. 0) → a sensible default suggestion based on dosage schedule is a good Phase 2+ heuristic; not required for MVP, noted rather than built.
  • Multiple medications low at once → one consolidated pickup suggestion listing all of them, not N separate prompts — same anti-notification-fatigue principle established in Daily Check-ins (Batch 1).

14Admin dashboard requirements

None new.

15Flutter project structure

apps/family_elder_app/lib/features/medications/refill/ — extends Module 5's feature folder rather than a separate top-level feature.

16Supabase requirements

One new table (medication_stock) + RLS. One new Postgres trigger. No new Edge Function, no new storage, no new consent category.

17Future scalability

The fixed unit vocabulary (tablets/ml/etc.) is chosen specifically so a future real-time pharmacy-stock integration (Phase 3+) has a clean mapping target instead of freeform text needing cleanup first.

Module 7 of 4 in this batch (7th overall)

Appointment Management

Tracks external medical appointments — a calendar fact the family is managing — distinct from, but optionally linkable to, a paid platform booking.

01Problem being solved

Elders have doctor visits, lab tests, and follow-ups that aren't platform bookings at all. Today there's no way to track them, and no connection between "elder has an appointment Tuesday" and "should we book a Hospital Companion for it."

02User personas

Family member
Primary — creates/edits/tracks appointments.
full
Elder
Views own, can add.
full, own record
Caregiver
Visible only if assigned to an accompanying booking.
read, booking-linked
Admin
None new.
none

03Functional requirements

  • CRUD: doctor/specialty, location, date/time, notes, reminder lead time.
  • An appointment is not a booking. A bookings row is paid, matched, and OTP-verified; an appointment is a calendar fact the family is tracking, optionally linked to a booking (e.g. if they book Hospital Companion to accompany it) via a nullable related_booking_id. Conflating the two would be a real modeling mistake this spec avoids on purpose.
  • Recurring appointments (e.g. monthly dialysis) via a simple fixed-cadence recurrence descriptor — not a full iCal RRULE for MVP.
  • Optional post-appointment outcome note.

04Non-functional requirements

Recurrence expansion must be efficient and idempotent, following the same generation-not-delivery pattern established in Module 5.

05User flow

1
FamilyAdds an appointment (one-off or recurring).
2
ReminderFires via Module 8 ahead of the appointment.
3
OptionalFamily taps "book a companion for this" → deep-links into the existing booking flow, date/time/location prefilled.
4
AfterFamily or elder can log an outcome note.

06Information architecture

Appointments list/calendar screen with a plain chronological list view as the accessible default (calendars are often harder to parse for lower digital literacy or visual impairment than a simple ordered list), add/edit form, detail view showing any linked booking and the outcome note.

07Database design

appointmentscalendar fact, not a transaction recordnew
elder_id, title, locationuuid fk / text / text—
scheduled_at, recurrence_ruletimestamptz / text, nullablesimple cadence descriptor, not full RRULE
related_booking_iduuid fk, nullableset only if a companion/transport service was booked for it
outcome_note, created_bytext, nullable / uuid fk—
statusenumscheduled / completed / cancelled

RLS reuses visit_history — an appointment is conceptually part of care/visit history, and inventing a new consent category here would be unwarranted sprawl (unlike Daily Check-ins in Batch 1, which genuinely needed one).

08API design

No Edge Function needed for CRUD — plain RLS-guarded writes. Recurrence expansion (turning a recurrence rule into concrete future instances) needs the same lightweight generation step as Module 5's dose generation, and should enqueue its reminders into Module 8's shared table rather than invent a fourth delivery path.

09Security design

No new sensitivity beyond existing visit_history-gated data.

10AI architecture

Not required. outcome_note is subject to the same never-unguarded-AI rule as every other free-text field in this plan if a future module ever summarizes it.

11Accessibility requirements

List-view-first design (see § IA) is itself the accessibility decision here.

12Notification requirements

Owned by Smart Reminder System (Module 8).

13Edge cases

  • A single instance of a recurring appointment is rescheduled without affecting the rest of the series — flagged as needing a documented decision (exception-instance table vs. keeping recurrence simple) rather than solved definitively; MVP scope keeps recurrence to fixed cadence only, no per-instance overrides.
  • The linked booking gets cancelled → the appointment itself must not auto-cancel. The doctor visit still exists even if the companion booking fell through — an explicit decoupling, not an oversight.

14Admin dashboard requirements

None new.

15Flutter project structure

apps/family_elder_app/lib/features/appointments/.

16Supabase requirements

One new table (appointments) + RLS reusing visit_history. No new Edge Function beyond the shared generation pattern noted above, no new storage, no new consent category.

17Future scalability

Simple fixed-cadence recurrence is an intentional MVP constraint; a full RRULE-based system is a plausible Phase 2+ upgrade once real usage shows the simple version is limiting.

Module 8 of 4 in this batch (8th overall)

Smart Reminder System

The shared reminder-delivery engine the previous three modules plug into — designed last in this batch, precisely because designing the other three first is what revealed it was needed.

01Problem being solved

Medicine Management, Medicine Refill Management, and Appointment Management each need to notify someone at a scheduled time. Building three separate sweep jobs and three delivery code paths would triduplicate the exact same problem. This module is the single shared engine; the other three own domain-specific generation (deciding what and when) and hand off delivery (getting a notification to a person, reliably, once) to this module.

02User personas

Elder
Receives reminders per recipient_scope.
read own
Family member
Receives reminders; can snooze/dismiss.
read, consent-scoped
Caregiver
Not a reminder recipient in this module's scope.
none
Admin
Sweep delivery-health visibility.
read-only, ops

03Functional requirements

  • Generic reminders table any module can enqueue into by referencing its own source row via source_type/source_id — deliberately not a hard foreign key (see § Database).
  • Delivery: FCM push primary, SMS fallback for low-connectivity or non-app-installed family members — reuses the existing FCM plan from PRD Part 2 §15, not a new push infrastructure.
  • Snooze and dismiss actions.
  • One unified sweep (reminders-dispatch-sweep) rather than per-module cron jobs.

04Non-functional requirements

  • Delivery must be idempotent — a sweep re-run must never double-send.
  • Must respect per-elder timezone and skip anything snoozed or already dismissed.

05User flow

Mostly infrastructure, not a destination screen. Reminders surface as push notifications, plus a simple in-app list aggregating every pending reminder regardless of which module generated it.

06Information architecture

Division of labor with the Family Notification Center (Batch 3)

This module produces the underlying scheduled trigger and owns delivery timing/channel selection. Batch 3's Family Notification Center owns the actual notification inbox UI and cross-source aggregation (SOS alerts, invite notifications, everything else). Stated explicitly here so the two aren't built later as duplicate, competing systems.

Consent-aware visibility varies per row, so the RLS policy needs a helper

A reminder about a medication dose is exactly as sensitive as the medication itself; a reminder about an appointment inherits visit_history. Because the required category depends on source_type, a single static policy can't express it — this needs one small helper function, required_consent_for_source(source_type), mapping source type to consent category, referenced inside the RLS predicate. This is the one piece of genuine new RLS design in this batch, called out precisely rather than glossed over.

08API design

POST/reminders/dispatch-sweep
New scheduled Edge Function, externally triggered (n8n/cron). Reads due, non-snoozed reminders, checks the source row still warrants sending (see § Edge cases), delivers via FCM/SMS, marks sent. The one delivery mechanism the other three modules in this batch all rely on.
—enqueue
Always a side effect of the source module's own write path (e.g. medications-generate-doses inserts a corresponding reminder) — no separate "create reminder" endpoint needed.

09Security design

Consent-aware visibility as designed above. SMS delivery touches a secret (SMS provider credentials), so the sweep is properly an Edge Function — consistent with the existing "secrets live in Edge Functions, never the client" rule.

10AI architecture

Not applicable.

11Accessibility requirements

Reminder copy must be short, plain-language, and deliberately non-alarming — a reminder is not an emergency, the same tone discipline established for Daily Check-ins' escalation messaging in Batch 1.

12Notification requirements

This module is the notification-generation engine for scheduled reminders; delivery UI/inbox belongs to Batch 3's Family Notification Center (see § IA).

13Edge cases

  • Source row deleted or discontinued after its reminder was enqueued but before it fires (e.g. a medication stopped) → the sweep must re-check the source's current state before sending, not blindly fire a stale reminder. A real correctness requirement given the loose reference design.
  • Multiple reminders for the same elder at the same instant, from different modules → ideally batched into one push rather than a notification storm; MVP can send them separately, noted as a known Phase 2+ improvement, not a blocker.

14Admin dashboard requirements

Ops visibility into sweep health (last run, delivery/failure rate). Plausibly the same admin page could cover every scheduled sweep in the platform (check-ins, doses, reminders) collectively rather than one page per job — worth flagging for whoever builds the admin side, not decided here.

15Flutter project structure

apps/family_elder_app/lib/features/reminders/ — mostly backend-driven; a simple aggregated list with snooze/dismiss actions.

16Supabase requirements

One new table (reminders), one new helper function (required_consent_for_source) and its RLS policy, one new scheduled Edge Function (reminders-dispatch-sweep). Supersedes the separate per-module sweep concepts sketched while designing Modules 5–7 above — this is the single point of delivery for all of them.

17Future scalability

The source_type/source_id loose-reference design is this module's core contribution to the rest of the 25-module plan: any future module can start enqueueing reminders without a single change to this table's schema. Index on (status, remind_at) is critical for sweep performance as adoption grows across modules.

Cross-cutting

Every touch to an existing, already-implemented module

None. This batch is fully additive new tables, functions, and screens — no column, policy, or existing Edge Function from the already-implemented booking/OTP/caregiver-verification/SOS/payments/DPDP modules is touched. The one place this batch connects to the existing system is a pure read/deep-link into the existing, unmodified bookings-create flow (Module 6, Medicine Refill Management) — no change to that function at all.
