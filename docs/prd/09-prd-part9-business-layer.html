Missing Modules, Batch 6: Business Layer

Part 9 of the Project Setu PRD, sixth of seven batches, and the one with the most direct pressure to touch the payments module — a subscription is inherently a billing concept. It doesn't. Care Plans introduces recurring charges through a table and an Edge Function entirely separate from the existing payments/payments-create-order/payments-webhook path, which stays untouched. Managed Elder Care Services needs one real, narrow authorization change to bookings-create; Care Analytics Dashboard needs none at all — it only reads.

Batch overview

Why subscription billing gets its own table, not a change to payments

payments today has one clean meaning: a family paid for one specific booking, merchant-of-record, via Razorpay Orders. A subscription fee isn't tied to a single booking — it's a recurring charge for an allocation of future visits, likely via a different Razorpay product (Subscriptions, not Orders) with its own status lifecycle. Bending payments to also mean "sometimes a recurring fee, sometimes a per-visit charge" would blur a table every existing report, reconciliation query, and refund flow already depends on having one meaning. A new, parallel care_plan_charges table keeps that boundary clean — this is the batch's one deliberate architectural stance, stated once here rather than re-argued in Module 21's own section.

Module 21 of 3 in this batch (21st overall)

Care Plans & Subscription Management

A recurring bundle of visits at a monthly price — orchestrating the existing, unmodified booking flow on a schedule, with its own billing path entirely separate from per-booking payments.

01Problem being solved

Every booking today is pay-per-visit. Families managing ongoing care want predictability — "3 companion visits a week plus a monthly nursing check" at one monthly price — rather than booking and paying for each visit individually.

02User personas

Family member
Subscribes an elder to a plan, manages pause/cancel.
full, own elder
Elder
Same visibility as family.
full, own record
Admin — super_admin
Manages the care-plan catalog, mirroring service catalog management.
catalog CRUD
Admin — finance_ops
Failed-charge queue, subscription billing oversight.
billing visibility

03Functional requirements

  • A per-region care-plan catalog (name, description, monthly price) each with allocations — a set number of visits of a given service_catalog service per week or month.
  • Family subscribes an elder to a plan; a scheduled job auto-generates that period's booking drafts against the allocation, calling the existing, unmodified bookings-create function — a legitimate, additive use of that function on a schedule rather than by a user tapping "book," not a change to it.
  • The monthly subscription fee covers allocated visits; anything beyond the allocation is billed per-visit through the existing, unmodified payment flow — a clear, statable hybrid rather than an ambiguous "sometimes included" model.
  • Pause (e.g. elder hospitalized — cross-references Hospital Companion Services, Batch 3) and cancel.
  • A failed subscription charge pauses future auto-generation until resolved — the plan never keeps committing the family to unpaid visits.

04Non-functional requirements

Visit-generation and billing are both scheduled batch jobs, not request-time operations — neither should ever block a family's live interaction with the app.

05User flow

1
FamilyBrowses the care-plan catalog, subscribes an elder to one.
2
WeeklyA scheduled job generates that period's booking drafts via the existing bookings-create, which then proceeds through the completely unmodified match → OTP flow.
3
MonthlyA separate scheduled job charges the subscription fee.
4
FamilyCan pause or cancel at any time; already-generated bookings for the current period are never silently reversed.

A care-plan catalog/browse screen, a subscription management screen (pause/cancel, view allocation usage), reachable from the Family Dashboard (Batch 1).

08API design

POST/care-plans/generate-visits
New scheduled Edge Function (weekly, n8n-triggered). For each active subscription's allocation, invokes the existing bookings-create function to generate that period's booking drafts — reuse, not reimplementation, of its validation logic.
POST/care-plans/billing-run
New scheduled Edge Function (monthly). Charges each active subscription via Razorpay's Subscriptions/recurring-charge product — a different Razorpay API surface than the Orders API payments-create-order already uses — and writes to care_plan_charges, never payments.

09Security design

Razorpay Subscriptions needs its own credentials

A new secret, Edge-Function-owned, following the existing "secrets never reach the client" rule — not assumed to be the same key as the Orders API without confirming with Razorpay's actual product boundaries.

10AI architecture

Not applicable.

11Accessibility requirements

Same baseline as the rest of the family-facing surface; plan comparison should favor plain-language allocation descriptions ("2 visits a week") over abstract pricing tables.

12Notification requirements

Charge success/failure, upcoming charge reminder, and pause/cancel confirmations, via the existing notification infrastructure (Batch 3) as new notification_types entries.

13Edge cases

  • Subscription charge fails → auto-generation pauses until resolved; the family is never left owing for visits the plan kept creating anyway. Full dunning/retry policy is a finance-ops design decision flagged here, not resolved by this spec.
  • Family cancels mid-period → already-generated bookings for that period are not auto-cancelled, the same decoupling principle already used for appointments (Batch 2) and hospital stays (Batch 3): an existing booking is a real commitment, not silently reversed by an unrelated status change elsewhere.
  • Elder covered by both a care plan allocation and a one-off manual booking of the same service in the same week → both simply coexist; the plan doesn't cap or block manual bookings.

14Admin dashboard requirements

Care-plan catalog management (super_admin), mirroring the existing service-catalog admin page. A failed-charge queue (finance_ops), in the same spirit as the existing payout reconciliation page.

15Flutter project structure

apps/family_elder_app/lib/features/care_plans/ — catalog browse, subscription management.

16Supabase requirements

Four new tables with RLS. Two new scheduled Edge Functions. No changes to payments, payments-create-order, or payments-webhook — confirmed explicitly, see § Cross-cutting.

17Future scalability

Plans are per-region from day one, following the same seam every other catalog-shaped table in this schema already uses — a Phase 2+ city with different pricing or allocation norms is a new row, not a schema change.

Module 22 of 3 in this batch (22nd overall)

Managed Elder Care Services

A concierge tier: a human care coordinator who can act on a family's behalf within defined operational boundaries — scheduling authority, never automatic health-data access.

01Problem being solved

Some families want less self-service and more concierge support — a dedicated coordinator who proactively manages bookings, appointments, and care-plan allocations rather than the family doing it all themselves.

02User personas

Family member
Retains full visibility and override; the coordinator supplements, never replaces, their access.
unchanged, full
Elder
Unchanged — a coordinator's operational authority never overrides the elder's own consent sovereignty.
unchanged, full
Care coordinator
New admin-scoped role, assigned to specific elders.
operational, not data-access — see § Security
Admin — super_admin
Manages coordinator assignments.
assignment CRUD

03Functional requirements

  • Coordinator-to-elder assignment (many elders per coordinator, one active coordinator per elder for MVP).
  • A coordinator can create bookings and adjust care-plan allocations on the assigned elder's behalf.
  • A coordinator's authority is operational (scheduling), not automatically an authority over health data. Reading elder_health_notes, elder_medications, or anything else consent-gated still requires the same has_consent() check as any other party — coordinator status grants none of that by itself. This boundary is the single most important design decision in this module.
  • Every coordinator action on an elder's behalf is logged to elder_timeline_events (Batch 1) — the same transparency mechanism already built for everything else, not a new logging system.

04Non-functional requirements

Coordinator assignment/removal must never retroactively affect bookings or care-plan state already in place — only future actions are affected.

05User flow

1
AdminAssigns a coordinator to an elder (a paid concierge-tier arrangement, business process outside this spec).
2
CoordinatorBooks visits, adjusts care-plan allocations, on the elder's behalf — logged to the elder's timeline.
3
FamilyCan still self-serve any of these actions at any time; the coordinator is additive, not exclusive.
4
Coordinator attempts to read health dataStill blocked by has_consent() exactly like anyone else without a grant.

06Information architecture

An admin dashboard extension: a "My Assigned Elders" view for the care_coordinator scope, reusing the family app's booking/care-plan screens' underlying data model rather than building a parallel UI paradigm.

07Database design

RLS: coordinator can select their own assignments; super_admin full access.

08API design

No new Edge Function required beyond the one authorization touch below — assignment CRUD is a plain admin-scoped RLS-guarded operation.

09Security design

The one necessary touch to an existing Edge Function in this batch

bookings-create's existing manual authorization check (isElderSelf || isLinkedFamily) needs one additive clause: || (has_admin_scope('care_coordinator') && assigned to this elder). This is the same pattern already used for the bookings-match preferred-caregiver tiebreak (Batch 3) — an additive OR condition to an existing check, not a rewrite of it, and it changes nothing about who's eligible to be booked, only who's allowed to initiate the booking request.

New admin_scope enum value: care_coordinator

An additive value on the existing admin_scope enum (PRD Part 2 §16), following the same enum-extension pattern already used for ai_interaction_type (Batch 4) and consent_category (Batch 1).

Operational authority is not data-access authority — restated as the module's core boundary

Named three times across this module because it's the one place a future implementer could accidentally grant a coordinator sweeping access "for convenience." They don't get it; they get exactly what bookings-create's existing authorization now additionally permits, and nothing else.

10AI architecture

Not applicable.

11Accessibility requirements

Not applicable — internal admin-facing role.

12Notification requirements

Family is notified when a coordinator is assigned or removed, and when a coordinator takes a booking action on their behalf — transparency, not a silent background process.

13Edge cases

  • Coordinator removed mid-active-booking → the booking itself is entirely unaffected; only future coordinator actions cease.
  • Family and coordinator both act on the same elder simultaneously → no conflict, both are just independent requesters under the existing booking model.
  • Coordinator attempts an action outside their assigned elders → blocked by the same RLS/authorization check, no special-casing needed beyond the assignment lookup itself.

14Admin dashboard requirements

Coordinator assignment management (super_admin) and the coordinator's own "My Assigned Elders" working view, both additive to the existing admin dashboard.

15Flutter project structure

Not applicable — this module is admin-dashboard (Next.js), not a Flutter surface.

16Supabase requirements

One new table (care_coordinator_assignments) with RLS. One additive admin_scope enum value. One additive authorization clause in the existing bookings-create function — the batch's one genuine existing-module touch, scoped as narrowly as the equivalent change in Batch 3.

17Future scalability

One-coordinator-per-elder is an MVP simplification; a future team-based coordination model (multiple coordinators sharing a caseload) is a plausible Phase 2+ extension to the assignment table's cardinality, not a redesign.

Care Analytics Dashboard

Internal ops reporting, and the place several earlier "feeds into analytics, not built here" cross-references finally land: suggestion accuracy (Batch 4), rating trends (Batch 5), scheduled-job health (Batches 2–3).

01Problem being solved

Ops has no aggregate view of how the platform is actually performing — booking volume trends, completion/cancellation rates, caregiver utilization, region-level breakdowns — and several modules in this plan deferred their own analytics needs here rather than building bespoke reporting each time.

02User personas

Admin — ops_admin
Full operational dashboards.
read-only, aggregate
Admin — finance_ops
Financial subset only.
read-only, scoped
Admin — super_admin
Everything.
read-only, full
Family, elder, caregiver
No access — this is a purely internal tool.
none

03Functional requirements

  • Booking volume over time, completion/cancellation rates, region-level breakdowns (using the existing region_id seam everywhere).
  • Caregiver utilization (bookings per active caregiver).
  • Rating trends (Batch 5), consolidated here rather than as a standalone page on the caregiver directory.
  • AI suggestion accuracy/dismissal rates (Batch 4).
  • Scheduled-job health (reminders, check-in sweeps, payouts, care-plan billing) — the single consolidated page floated as an idea in Batches 2, 3, and 6, built for real here.
  • Aggregate and statistical only — no PII, no health content, ever, matching the existing PostHog principle (PRD Part 2 §15: "anonymized/categorical properties only").

04Non-functional requirements

Dashboard queries must not compete with live transactional load — see § Database for the materialized-view approach.

05User flow

1
Ops adminOpens the Analytics page, sees operational trends with a visible "last updated" timestamp.
2
Finance opsSees the financial subset only.

06Information architecture

A new Analytics section in the admin dashboard, scope-gated per the table above — this module is primarily an admin dashboard addition.

07Database design

Materialized views, refreshed on a schedule — not live aggregate queries

Running aggregate queries against live transactional tables on every dashboard load would compete with real traffic. Materialized views (mv_booking_volume_daily, mv_caregiver_utilization, mv_rating_trends, and similar), refreshed periodically, keep dashboard reads cheap and keep the underlying tables' performance unaffected by how often ops checks the dashboard. The refresh mechanism itself (a Postgres-native scheduled refresh vs. an external cron trigger) is an implementation choice, not specified further here.

RLS/access on the views restricted to the relevant admin scopes per § Personas.

08API design

No new Edge Function for reads — the admin dashboard queries the materialized views directly via its existing request-scoped Supabase client, same pattern as every other admin page. The periodic refresh is the only new scheduled operation this module needs.

09Security design

Distinct from PostHog, on purpose

PostHog (PRD Part 2 §15) already tracks product analytics — how families use the app. This module is care-operation analytics — how the operation is performing. Naming the distinction here prevents the two from later being conflated as the same system serving two audiences with very different access needs.

10AI architecture

Not applicable — this module consumes AI Recommendation Engine's (Batch 4) suggestion-outcome data as an input metric; it generates no AI content itself.

11Accessibility requirements

Standard admin-dashboard accessibility (this is a desktop ops tool, not an elder-facing surface — see PRD Part 2 §10 on why the admin dashboard is web, not Flutter).

12Notification requirements

None — a pull dashboard, not a push system.

13Edge cases

  • A region with very low volume → small-sample statistics (e.g. "100% cancellation" from one booking) must be visually flagged as low-confidence, not presented with the same weight as a large-sample stat — a real statistics-communication requirement, not just a display nicety.
  • Materialized view staleness → every figure carries a visible "as of [refresh time]" label so ops never mistakes it for real-time.

14Admin dashboard requirements

This module's entire scope is admin dashboard requirements — see §§ 02, 06.

15Flutter project structure

Not applicable.

16Supabase requirements

Several new materialized views (no new base tables). A periodic refresh mechanism. No new Edge Function, no new consent category, no touch to any existing table's schema or RLS.

17Future scalability

Region-level breakdowns are native to every view from day one via the existing region_id seam — a Phase 2+ city or country doesn't need a new dashboard, just a new filter value on ones that already exist.
