Missing Modules, Batch 3: Visits & Records

Part 6 of the Project Setu PRD, third of seven batches. This batch has a different shape from the first two: two of its four modules (Companion Visits, Hospital Companion Services) build on service types that already exist and already work in service_catalog — the question for each was specifically "what's missing beyond just being able to book this," not "how do we add this service." The other two (Family Notification Center, Health Records Management) give a UI and a proper security boundary to data that already exists in bare form (notifications, scattered health fields) but was never designed as a real module.

Batch overview

Two already-bookable services, two already-bare tables

hospital_companion and companionship_visit are live entries in the seeded service catalog today — a family can already book either one and run it through the full existing bookings-create → bookings-match → OTP flow with no changes at all. What those two modules below actually specify is the richness a single isolated booking can't express: visit continuity with a preferred caregiver, shift-to-shift handoff during a multi-day hospital stay, structured activity logs. Meanwhile notifications and the health-adjacent fields already scattered across elder_health_notes/elder_medications get their first real product surface in this batch, not their first table.

Module 9 of 4 in this batch (9th overall)

Family Notification Center

The existing notifications table already receives writes from sos-trigger and me-erasure-request — there has simply never been an inbox screen, a read/unread model, or a preferences layer built on top of it.

01Problem being solved

Notifications are being written today with no way for a recipient to see them as a list, mark them read, or choose which channel a given category arrives on. Every module that needs to notify someone (Smart Reminder System, Family Member Management, SOS) currently has nowhere coherent to send them.

02User personas

Family member
Full inbox + preferences.
own notifications only
Elder
Separate, simplified view — fewer categories, no preference matrix.
own notifications only
Caregiver
Job-related notifications only (new assignment, payout status), same underlying table.
own notifications only
Admin
Delivery-health visibility, not individual message content.
aggregate, read-only

03Functional requirements

  • Unified inbox: chronological, filterable by type, read/unread, mark-all-read, badge count.
  • Deep-link from each notification to its source screen.
  • Per-type channel preference (push / SMS / in-app-only / push+SMS).
  • Certain notification types cannot be disabled — SOS-class and the missed-check-in escalation from Batch 1 are safety-adjacent enough that family may choose channel but never turn them fully off. Enforced structurally, not by convention — see § Database.
  • Elder-mode gets a reduced category set (SOS confirmation, "family checked on you," visit reminders) with no configuration surface — family manages preferences on the elder's behalf.

04Non-functional requirements

  • SOS-class delivery latency budget: under 5 seconds from trigger to device.
  • Preferences must never silently degrade a must-deliver category — the enforcement described below is a hard constraint, not a UI nudge.

05User flow

1
Any userTaps the bell icon (badge shows unread count) → inbox.
2
Tap a notificationDeep-links to its source (booking, SOS monitor, reminder origin).
3
SettingsFamily member sets per-type channel preference; cannot disable must-deliver types.

06Information architecture

Notification inbox (new screen), notification preferences (new screen), bell icon with badge in main nav (additive UI element, not a change to existing navigation logic).

Reuses the existing notifications table as-is — no changes to it. Three new tables:

08API design

No new Edge Function. Reading the inbox and writing preferences are both plain RLS-guarded operations. Actual delivery dispatch (SMS/push) stays owned by whichever module generates a given notification — sos-trigger, reminders-dispatch-sweep, family-invite — this module is presentation and preference, not a delivery pipeline, per the division of labor stated in Batch 2's Module 8.

09Security design

Must-deliver enforcement is a database trigger, not a UI restriction

A BEFORE INSERT OR UPDATE trigger on notification_preferences joins notification_types and raises an exception if enabled = false is attempted for a can_disable = false type. This mirrors the stock-decrement trigger pattern from Batch 2 — a cross-cutting invariant belongs in the database, not duplicated across every client that could write this row.

No new consent category

A user's own notification preferences aren't elder health data — they're the recipient's own settings, gated by user_id = auth.uid() exactly as notifications already is.

10AI architecture

Not applicable.

11Accessibility requirements

Elder-mode's reduced category set (§ FR) is the accessibility decision here — no dense preference matrix for elders, ever.

12Notification requirements

This module is the presentation layer for every notification type in the system — recursive by nature, no further sub-requirement.

13Edge cases

  • Notification references a since-deleted or cancelled source → tapping shows "this is no longer available" gracefully, not a crash.
  • Zero notifications ever → empty state.
  • Multiple devices per user → push targets every registered, recently-seen token, not just the most recent one.

14Admin dashboard requirements

Delivery-health visibility (success/failure rate by channel) — plausibly the same consolidated "scheduled jobs health" admin page floated in Batch 2, covering reminders, check-in sweeps, and notification delivery together rather than three separate pages.

15Flutter project structure

apps/family_elder_app/lib/features/notifications/ — NotificationInboxScreen, NotificationPreferencesScreen, NotificationBell. apps/caregiver_app gets its own lightweight inbox variant, job-related types only.

16Supabase requirements

Three new tables (notification_types, notification_preferences, user_devices) with RLS, one new trigger. notifications itself is unchanged. No new Edge Functions, no new consent category.

17Future scalability

notification_types as a config table means Batches 4–7 register new types with a data insert, not a schema migration — the same extensibility principle as reminders.source_type in Batch 2.

Module 10 of 4 in this batch (10th overall)

Companion Visits

companionship_visit already books and completes today. This module adds caregiver continuity and a structured activity log — the two things that turn a one-off booking into an actual relationship.

01Problem being solved

A family can already book a companionship visit and it runs through the existing flow correctly. What's missing is everything that makes repeat companion care feel like a relationship rather than a stranger every time: no way to request the same caregiver again, and no record of what actually happened during the visit beyond "completed."

02User personas

Family member
Sets caregiver preference and interests.
full, consent-gated
Elder
Same visibility as family for their own preferences.
full, own record
Caregiver
Logs the activity record during/after an assigned visit.
booking-scoped write
Admin
None new required.
none (MVP)

03Functional requirements

  • Preferred-caregiver setting per elder, plus a small structured list of interests (e.g. walking, cards, reading) — not freeform text, so it can drive matching without needing NLP.
  • Preferred-caregiver continuity in matching: when a preference is set, bookings-match should prefer that caregiver among otherwise-eligible candidates, falling back to normal matching if they're unavailable or no longer eligible. This is the one place in this batch that touches an existing Edge Function — flagged fully under § API and in the batch's cross-cutting section, because there's no other way to express "prefer this caregiver" without touching the function that does caregiver selection.
  • Structured visit activity log: fixed checklist (walked, played a game, read together, watched TV, other) plus a caregiver-observed mood (small fixed vocabulary, mirroring Daily Check-ins' mood field) and a short capped note.

04Non-functional requirements

The matching preference must never reduce trust-tier safety — a preferred caregiver who no longer meets the service's required trust tier is never selected, preference or not.

05User flow

1
FamilySets a preferred caregiver (optional) and interests once.
2
Every future companion bookingMatching prefers that caregiver automatically — no need to re-request each time.
3
CaregiverDuring or right after the visit, logs the activity checklist + observed mood.
4
FamilySees the log on the Family Dashboard / Timeline (Batch 1).

06Information architecture

Preference settings live under the elder's profile. Activity logs surface as Timeline entries and on the relevant booking's detail screen — not a separate top-level app section.

07Database design

RLS for both: is_elder_self, has_consent('visit_history'), is_admin, plus — for visit_activity_logs writes only — the assigned caregiver during an in_progress or just-completed booking, the same shape as elder_health_notes_insert.

08API design

—preferences, activity log
Both plain RLS-guarded writes — no secret, no cross-table rule beyond the policies above.

The one existing-module touch in this batch: bookings-match

Add a single additive tiebreak to the existing candidate query: among caregivers who already pass the current trust-tier/region/type eligibility filter unchanged, prefer companion_visit_preferences.preferred_caregiver_id if present in the eligible set; otherwise fall back to today's selection exactly as-is. This does not change what makes a caregiver eligible — only which eligible caregiver is picked first. Scoped this narrowly and stated explicitly because it is the only place in Batches 1–3 that modifies an already-implemented Edge Function's logic, not just its data.

09Security design

No new sensitivity beyond existing visit_history-gated data. The matching preference carries no security weight — it cannot make an ineligible caregiver eligible, only reorder eligible ones.

10AI architecture

Not required. Activity notes are subject to the standing never-unguarded-AI rule if ever summarized by a future module.

11Accessibility requirements

Same baseline as prior batches; the activity checklist uses icons + short labels, consistent with the platform's low-literacy-friendly pattern.

12Notification requirements

None new — activity logs surface passively via Timeline (Batch 1), no separate alert.

13Edge cases

  • Preferred caregiver becomes inactive or drops below required trust tier → matching falls back silently to normal selection this time; a "your regular companion wasn't available" family notification is a reasonable Phase 2+ addition, not required for MVP.
  • No interests set yet → checklist and matching both still function; nothing blocks on an empty preference.

14Admin dashboard requirements

None new for MVP.

15Flutter project structure

apps/family_elder_app/lib/features/companion_visits/ — preference settings screen, activity log viewer (feeds Timeline). apps/caregiver_app gets an activity-log entry form scoped to companion-type bookings.

16Supabase requirements

Two new tables with RLS. One additive, narrowly-scoped tiebreak added to the existing bookings-match query (see § API risk callout above). No new consent category, no new storage.

17Future scalability

Structured interests/activities jsonb (not freeform) means a future recommendation feature (Batch 4's AI Recommendation Engine) can reason over them directly rather than needing NLP extraction from prose first.

Module 11 of 4 in this batch (11th overall)

Hospital Companion Services

A single hospital_companion booking already works. This module coordinates a series of them into one continuous hospital stay with shift handoff — without changing the bookings table at all.

01Problem being solved

Hospital stays span days and shifts. Today, family covering a multi-day admission would have to create disconnected bookings with no shared context between them — no way to see "3 shifts covered, 1 gap tomorrow morning," and no way for one caregiver to hand off context to the next.

02User personas

Family member
Creates the stay, books shifts against it, sees coverage.
full
Elder
Same visibility as family for their own stay.
full, own record
Caregiver
Leaves/reads handoff notes for shifts within the same stay, not just their own.
stay-scoped, not booking-scoped
Admin
None new required.
none (MVP)

03Functional requirements

  • "Hospital Stay" record: hospital name/location, admission date, expected/actual discharge, status.
  • Multiple hospital_companion bookings (shifts) linked to one stay via a junction table — deliberately not a new column on bookings, so the existing, already-implemented booking module is touched not at all.
  • Shift handoff note: the caregiver ending a shift can leave a brief note visible to family and to whichever caregiver covers the next shift on the same stay — not just their own booking.
  • Coverage gap visibility: a stay with no shift booked for the next several hours should be visually flagged to family.
  • Family marks the stay discharged when the elder leaves hospital, closing it.

04Non-functional requirements

Gap detection feeds the shared Smart Reminder System (Batch 2) as a new source_type, rather than a bespoke alert mechanism built just for this module.

05User flow

1
FamilyCreates a Hospital Stay record on admission.
2
FamilyBooks multiple hospital_companion shifts via the unmodified existing booking flow, each linked to the stay.
3
CaregiverEnding a shift, leaves a short handoff note.
4
Next caregiverReads the prior shift's note before their own shift starts.
5
FamilyMarks the stay discharged; any still-scheduled shift prompts a cancellation confirmation, never an automatic cancel.

06Information architecture

Hospital Stay detail screen showing a shift timeline (each linked booking + its handoff note), reachable from the elder's care overview. Individual shift bookings still appear in the normal bookings list too — the stay is a grouping lens, not a replacement screen.

07Database design

elder_id, hospital_nameuuid fk / text—

status, created_byenum / uuid fkactive / discharged / cancelled

RLS for both new tables mirrors bookings_select's shape (elder self, linked family with visit_history consent, admin). One deliberate extension: a caregiver may read hospital_stay_bookings rows for a stay if they are assigned to any booking within that same stay — not only their own — which is exactly what handoff continuity requires. This is a new, narrowly-scoped policy on a new table, not a change to any existing booking-visibility policy.

08API design

No new Edge Function. Creating a stay, linking a booking to it, and writing a handoff note are all plain RLS-guarded operations against the two new tables above. Booking creation itself still goes through the unmodified, existing bookings-create/bookings-match flow.

09Security design

The one genuinely new access decision in this module — a caregiver seeing another caregiver's shift note within the same stay — is scoped precisely to that junction table and justified by the handoff use case; it does not extend to seeing anything else about the elder outside this specific stay.

10AI architecture

Not required.

11Accessibility requirements

Same baseline as the rest of this batch.

12Notification requirements

Coverage-gap alerts route through Smart Reminder System (Batch 2), not a bespoke mechanism.

13Edge cases

  • Overlapping shifts booked by mistake (or on purpose, e.g. for a difficult transfer) → warn, don't block; a genuine judgment call left to family, not auto-prevented.
  • Stay marked discharged with a shift still scheduled → prompts a cancellation confirmation; never auto-cancels, mirroring the appointment/booking decoupling principle from Batch 2.

14Admin dashboard requirements

None new for MVP — ops can already see the individual underlying bookings.

15Flutter project structure

apps/family_elder_app/lib/features/hospital_stays/. apps/caregiver_app gets a handoff-note entry point scoped to hospital_companion bookings linked to an active stay.

16Supabase requirements

Two new tables with RLS (including the one deliberately extended cross-caregiver read policy above). No changes to bookings. No new Edge Function, no new consent category.

17Future scalability

The junction-table design (rather than a column on bookings) is what keeps this module fully additive — the same pattern is available to any future module needing to group existing bookings without touching the booking module itself.

Module 12 of 4 in this batch (12th overall)

Health Records Management

A static reference profile — allergies, conditions, physician contact, insurance — distinct in shape from the append-only visit logs elder_health_notes already handles.

01Problem being solved

elder_health_notes is an append-only log of what happened at visits; elder_medications tracks current prescriptions. Neither has anywhere to put slow-changing reference information — allergies, chronic conditions, blood type, primary physician, insurance — that any caregiver dispatched to this elder needs as context, not something generated by a specific visit.

02User personas

Family member
Maintains the profile.
health_notes consent
Elder
Full access to own profile.
full, own record
Caregiver — emergency-relevant half only
Sees allergies/conditions/blood type/emergency notes during an active booking or SOS response.
booking/SOS-scoped, life-safety override
Admin
None new.
none (MVP)

03Functional requirements

  • Two-tier profile, split precisely by who needs to see what in an emergency versus who manages administrative logistics — see § Database for why this is two tables, not one.
  • Structured (not freeform) allergies and chronic-conditions lists — enables future drug-interaction or care-planning features without a schema change later.
  • Editable by family/elder at any time; every change is a straightforward update, not versioned for MVP (a full change-history is a plausible Phase 2+ addition once real usage shows it's needed, not built speculatively now).

04Non-functional requirements

Emergency-relevant fields must be readable by a caregiver in under one query, no multi-hop joins, since this data matters most in exactly the moment there's no time to spare.

05User flow

1
Family / elderFills in the profile once, updates as things change.
2
CaregiverAssigned to a booking or SOS response, sees the emergency-relevant fields automatically — no consent negotiation needed in the moment, the same principle already established for sos_events.
3
Admin/billing contextInsurance and physician contact stay family/elder/admin-only, never surfaced to a caregiver.

06Information architecture

One "Health Profile" screen for family/elder editing, split visually into an emergency-info section and an administrative-info section, matching the underlying data split.

07Database design

Split by who needs it in an emergency, not by topic

Insurance and physician contact are administrative; allergies and DNR-equivalent notes are literally life-safety. A single table would force an all-or-nothing choice about caregiver visibility. Splitting means a non-clinical companion caregiver present during a medical emergency can see "penicillin allergy" without also seeing an insurance policy number they have no reason to need.

RLS on elder_health_profile: is_elder_self, has_consent('health_notes'), is_admin, plus the assigned caregiver during an active booking or an active SOS for this elder — the latter clause is a direct, reasoned extension of the existing principle that life-safety visibility overrides granular consent, already established for sos_events, not a new precedent invented here. RLS on elder_administrative_profile: identical shape minus the caregiver clause entirely — no caregiver override, ever.

08API design

No new Edge Function — both tables are plain RLS-guarded reads/writes, reusing is_assigned_caregiver() and the existing SOS-active check pattern rather than inventing new authorization primitives.

09Security design

Both sensitive columns get column-level encryption

emergency_medical_notes and insurance_policy_number qualify squarely under the existing PRD Part 2 §13 rule ("government ID numbers and raw medical notes are encrypted at the column level") — applying an already-decided pattern to new columns, not inventing new security infrastructure.

Single consent category, by design, with the trade-off named

Both new tables reuse health_notes rather than splitting into a separate category — even though insurance data is arguably less sensitive than a DNR-equivalent note. Introducing a second category for one table would be disproportionate complexity for MVP; flagged here as a deliberate simplification rather than an oversight.

10AI architecture

Not applicable. Structured allergy/condition lists exist partly so a future AI feature (Batch 4) could reason over them without needing to parse prose — noted, not built here.

11Accessibility requirements

Same baseline; the profile form uses simple structured pickers for allergies/conditions rather than free-text entry wherever possible, both for accessibility and for the structured-data benefit noted above.

12Notification requirements

None — this module is a reference profile, not an event stream.

13Edge cases

  • Non-clinical caregiver on a companionship visit still sees elder_health_profile (allergies, emergency notes) during that active booking — intentional: anyone present when something goes wrong needs emergency-relevant information, regardless of clinical training. They never see elder_administrative_profile.
  • Elder has no known allergies/conditions → fields are simply empty, not a blocking requirement to fill in before booking.
  • Profile edited while a caregiver is mid-visit → the caregiver's next read reflects the update immediately, same "no cache, RLS-guarded live query" principle as everything else in this schema.

14Admin dashboard requirements

None new for MVP. A printable/quick-view "elder emergency card" for ops use is a plausible Phase 2+ addition, not specified further here.

15Flutter project structure

apps/family_elder_app/lib/features/health_profile/. apps/caregiver_app surfaces the emergency-relevant half read-only, scoped to active bookings/SOS.

16Supabase requirements

Two new tables with RLS (one with a caregiver life-safety-override clause, one without), reusing the existing health_notes consent category and the existing column-encryption pattern. No new Edge Function, no new consent category, no new storage.

17Future scalability

Structured allergy/condition data is the foundation for later clinical-decision-support-adjacent features (still never diagnostic, per the platform's standing AI rule) without a schema migration first.

Cross-cutting

Every touch to an existing, already-implemented module

One touch in this entire batch, and it's precisely scoped:

Existing moduleWhat's addedWhy it's necessary
bookings-match (Edge Function)One additive tiebreak in the candidate query: prefer companion_visit_preferences.preferred_caregiver_id among already-eligible candidatesThere is no way to express "prefer this caregiver" without touching the one function that selects a caregiver. Eligibility itself (trust tier, region, type) is completely unchanged — only the order of selection among already-eligible candidates.

Everything else in this batch — including the entire Hospital Companion Services module — was deliberately designed to avoid touching bookings, notifications, or any other existing table's schema, using junction tables and config tables instead.
