Missing Modules, Batch 7: Trust & Safety

Part 10 of the Project Setu PRD, the seventh and final batch. Both modules here sit directly adjacent to the two most safety-critical systems already built — the DPDP consent model and SOS — which is exactly why they were scheduled last rather than first: every architectural habit established across Batches 1–6 (additive-only touches, named trade-offs, junction tables over new columns, separate tables over overloaded ones) gets applied here at its highest stakes, not invented under pressure at the start.

Batch overview

Neither module rebuilds what already exists

The consent model (consent_grants, has_consent(), RLS as the enforcement layer) and the SOS flow (108-first, sos-trigger, life-safety-overrides-consent) are both already fully implemented and explicitly off-limits to modification. It would have been easy to scope these two modules as "improve consent" and "improve SOS" and end up quietly rewriting both. Instead, each module below is scoped to something specific and already named as missing in the existing codebase's own comments and prior batches' cross-references — not invented fresh, and not a rewrite of anything that works today.

Module 24 of 2 in this batch (24th overall)

Consent & Privacy Management

Three things the existing consent/DPDP backend has always been able to support but never had a UI or workflow for — each one named as future work in the codebase's own comments before this module existed.

01Problem being solved

The consent-grant model, the guardian-override path (consent_grants.granted_via = 'documented_guardian_process'), me-data-export, and me-erasure-request already exist. Three things don't: a real UI making any of this usable end to end, an actual review workflow for guardian-override requests (PRD Part 2 §13 calls this out explicitly as needing to be "a real workflow, not a checkbox," deferred to exactly this kind of module), and the elder-facing "who accessed my data" view that migrations/0002_rls.sql's own comment on audit_log named as a Part 3/4 feature "built on top of this table through a dedicated Edge Function, not raw RLS."

03Functional requirements

  • Privacy Center screen: every consent_grants row for the elder in one place, grant/revoke with a single tap — a UI layer over an access model that already fully supports this, not a new access model.
  • Guardian-override request queue: a family member submits a request (category, basis description, optional supporting document) for an elder who lacks capacity to consent themselves. An admin reviews and approves or denies — approval means the admin performs the actual grant through the existing, already-permitted consent_grants_write policy path (granted_via = 'documented_guardian_process' and is_admin()), which needs no change at all.
  • "Who accessed my data": an elder-facing view over audit_log, translating raw resource_type/resource_id rows into a readable "who did what, when" list scoped to entries that trace back to this elder — the dedicated-Edge-Function approach the existing RLS migration's own comment called for, not a direct RLS policy on audit_log (which can't express "does this row belong to me" generically across every resource type).
  • Existing me-data-export/me-erasure-request functions get a real UI entry point for the first time — they've only been exercised via direct HTTP calls so far.

04Non-functional requirements

An honest limit on "who accessed my data," stated plainly

audit_log today only receives write-path events — every state-mutating Edge Function logs to it, but nothing logs a read yet (the gap named repeatedly since Batch 1's Family Dashboard and Timeline sections). This feature therefore shows real data — bookings, payments, SOS events, erasure requests — but cannot yet show "family member X viewed your medication list on this date," because nothing generates that event today. The feature's value grows exactly as more read paths adopt logging; it is not silently more complete than what actually exists.

09Security design

Zero touches to the consent enforcement layer itself

This module is presentation (Privacy Center), a previously-deferred read (access history), and a request queue in front of a grant mechanism that was already fully permitted. consent_grants, has_consent(), and every RLS policy that depends on them are unchanged by this module, full stop.

11Accessibility requirements

The Privacy Center is one of the highest-stakes screens for plain language — every consent category label must be understandable without legal or technical vocabulary, consistent with the platform's low-digital-literacy design principle throughout.

12Notification requirements

Guardian-override request submitted/approved/denied, via the existing notification infrastructure (Batch 3).

13Edge cases

  • Guardian-override request denied → the family member is notified with the admin's stated reason where appropriate; the elder's default of no access remains, exactly as it should.
  • Elder later regains capacity and wants to review/revoke a guardian-granted category themselves → the existing consent_grants_write policy already allows is_elder_self to revoke any grant regardless of how it was originally created — no new logic needed, confirmed rather than assumed.
  • Access history requested for an elder with zero logged write-path events yet → an honest empty state explaining what the view currently covers, not a blank screen with no context.

14Admin dashboard requirements

A guardian-override review queue, additive to the admin dashboard, in the same shape as the existing erasure-requests review page (Batch 1's Family Member Management era work) — approve/deny with notes, not a novel workflow pattern.

15Flutter project structure

16Supabase requirements

One new table (guardian_consent_requests) with RLS reusing the existing consent_category enum. One new Edge Function (me-access-history). No changes to consent_grants, has_consent(), or any existing consent/DPDP policy or function.

17Future scalability

me-access-history's value scales directly with how many read paths eventually adopt audit_log instrumentation — this module doesn't need to change as that gap closes elsewhere; it just starts surfacing more.

Module 25 of 2 in this batch (25th overall, final module)

Enhanced Emergency Services

Four additions around the existing, untouched sos-trigger flow — one small enrichment to its payload, three entirely new and separate capabilities, with the practice/drill mode kept structurally incapable of being confused with a real emergency.

01Problem being solved

SOS triggering, 108-first enforcement, and family/ops notification fan-out already work. Four real gaps remain: responders don't automatically see the elder's emergency-relevant medical info, ops has no distance-based suggestion for who to dispatch, nothing captures a structured post-incident record, and there's no safe way for a family to practice the flow before they need it for real.

02User personas

Elder / family
Triggers real SOS (unchanged) or a drill (new, clearly separate).
unchanged for real SOS; new for drills
Admin — sos_operator
Sees enriched medical context, a responder suggestion, files the incident report.
existing scope, extended surface
Caregiver
Unchanged.
unchanged

03Functional requirements

  • SOS notifications sent to family and ops include a snapshot of the elder's emergency-relevant health profile (allergies, chronic conditions, blood type, emergency notes from Batch 3's elder_health_profile) — read via the life-safety-override RLS clause Batch 3 already established for exactly this purpose, not a new access rule.
  • A nearest-available-responder suggestion for the ops-facing SOS monitor, based on available location signals (active-booking caregiver locations, registered service-area radius from Caregiver Management, Batch 5) — a suggestion for a human to act on, never automatic dispatch. Emergency response assignment stays a human decision, consistent with every other place in this plan where automation proposes and a person decides.
  • A structured post-incident report, filed by ops after resolution: whether 108/local EMS was actually engaged, an outcome summary, optional lessons notes — a QA and documentation layer, not a blocker on the resolution flow itself.
  • A practice/drill mode, walking through the same 108-first screen and confirmation flow as a real SOS, for family/elder familiarity — entirely separate data path from real SOS events, never fanning out real family/ops notifications, and visually unmistakable as practice throughout.

04Non-functional requirements

The nearest-responder suggestion is explicitly best-effort — caregiver location is only known during active bookings today, so coverage is partial by design, and the UI must say so rather than implying a comprehensive dispatch system that doesn't exist.

05User flow

1
Real SOSTriggered exactly as today; the notification ops and family receive now additionally includes the elder's emergency-relevant medical snapshot.
2
OpsSees a best-effort nearest-responder suggestion on the SOS monitor, decides and dispatches manually.
3
Ops, after resolutionFiles a structured incident report.
4
Family/elder, separatelyCan run a practice drill any time, reached through an "Emergency Preparedness" area distinct from the real SOS button — never adjacent to it, to eliminate mis-tap risk.

06Information architecture

Real SOS UI is entirely unchanged. Drill mode lives in a separate "Emergency Preparedness" settings area, deliberately not co-located with the live SOS trigger. The admin SOS monitor (existing page) gains an incident-report form and a responder-suggestion panel as additive sections.

sos_drills is a completely separate table from sos_events — this is the module's central safety decision

Co-mingling drills and real events in one table, even with an is_drill flag, creates a standing risk that any future query, report, or admin view that forgets to filter it treats a drill as real or a real event as practice — for a life-safety table, that risk is unacceptable regardless of how small it seems at design time. A structurally separate table makes that class of bug impossible rather than merely unlikely.

09Security design

The one touch to sos-trigger in this entire batch, stated precisely

Enriching the notification payload it already constructs with elder_health_profile's emergency-relevant fields, read via the life-safety-override RLS clause Batch 3 already put in place for exactly this scenario. The trigger, escalation, and status logic are completely unmodified — only what's included in the message being sent changes.

Drills never touch real notification infrastructure

sos-drill-trigger gives feedback only to the practicing user's own device — no family push, no ops alert, no notifications row indistinguishable from a real one. Stated explicitly to prevent both alarm fatigue and any possibility of a drill being mistaken for a real emergency by anyone but the person running it.

10AI architecture

Not applicable.

11Accessibility requirements

Drill mode must be at least as accessible as the real SOS flow it practices — the entire point is building elder familiarity and confidence with a screen they may one day need to use under stress.

12Notification requirements

Real SOS notifications are unchanged except for the medical-info enrichment above. Drills generate no external notifications by design (see § Security).

13Edge cases

  • Elder or family triggers a drill thinking it might be treated as real by ops → structurally impossible, since drills never reach sos_events, notifications, or the ops SOS monitor at all.
  • Nearest-responder suggestion has no location data available → shows "no location-based suggestion available, use standard dispatch," never a broken or misleadingly empty panel.
  • Incident report never filed → the underlying sos_event's own resolution status is completely unaffected; the report is documentation, not a gate.

14Admin dashboard requirements

Incident report filing and the responder-suggestion panel, both additive to the existing SOS monitor page. A separate drill-history view for ops visibility into practice-mode usage (distinct from, never mixed with, the real SOS event list).

15Flutter project structure

apps/family_elder_app/lib/features/emergency_preparedness/ — drill entry point and flow, structurally and visually separated from the existing real SOS trigger screen.

16Supabase requirements

Two new tables (sos_incident_reports, sos_drills) with RLS. One new Edge Function (sos-drill-trigger), deliberately independent of sos-trigger. One small, precisely-scoped enrichment to sos-trigger's existing notification payload — the batch's only touch to that function's behavior.

17Future scalability

The nearest-responder suggestion's coverage improves automatically as Caregiver Management's availability/location data (Batch 5) matures — no redesign needed here when that happens, just a richer input to a query that already exists.

All 25 modules specified

Seven batches, 25 modules, architecture and requirements only — no implementation code, as instructed throughout. Across the full plan, the total footprint on the six already-implemented modules (booking, OTP verification, caregiver verification, SOS, payments, DPDP) is: three additive enum values (consent_category, ai_interaction_type ×3, admin_scope), one additive column pair on family_links/elder_profiles, one additive tiebreak and one additive authorization clause in bookings-match/bookings-create, and one additive notification-payload enrichment in sos-trigger. The payments table and both payment Edge Functions were never touched at all. Every other new capability across all 25 modules — dozens of new tables, a dozen-plus new Edge Functions, three new consent-respecting RLS patterns — is fully additive, built alongside the existing system rather than through it.
