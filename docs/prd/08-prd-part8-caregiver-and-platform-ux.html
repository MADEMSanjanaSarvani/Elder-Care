Missing Modules, Batch 5: Caregiver Ops & Platform UX

Part 8 of the Project Setu PRD, fifth of seven batches. The first two modules extend the already-implemented caregiver-verification core (trust tier, BGV, police verification — all untouched) with the operational layer around it: profile, availability, deactivation history, and a genuinely new signal — service-quality rating, kept deliberately separate from trust tier. The last two modules formalize something every prior batch has been informally assuming exists: a real accessibility system and a real multi-language system, referenced from Batch 1 onward, specified here for the first time.

Batch overview

Vetting and quality are different axes — and this batch is where that gets said out loud

trust_tier answers "is this caregiver credentialed and safe to dispatch" — background check, police verification, clinical council registration. It says nothing about whether families who've actually received care from them were happy with the visit. A newly-onboarded probationary caregiver can give excellent care; a long-verified clinical_verified nurse can have a bad week. Module 18 below introduces service-quality rating as a genuinely separate signal, explicitly not folded into trust_tier or computeTrustTier() — conflating the two would corrupt a vetting signal the platform depends on for safety with a satisfaction signal that's inherently softer and more subjective.

Module 17 of 4 in this batch (17th overall)

Caregiver Management System

Verification (BGV, police, trust tier) already works end to end. This module is everything else a real caregiver workforce needs: a profile, an availability schedule, and an accountable deactivation trail.

01Problem being solved

caregivers today has verification fields and a bare active boolean — no profile a family sees beyond a name and trust tier, no availability concept at all (matching assumes every active caregiver is always available), and no record of why a caregiver was ever deactivated.

02User personas

Caregiver
Self-manages profile, availability, sees own onboarding checklist.
own record
Family member
Sees the richer profile on the Care Team card.
read, no consent gate needed — same visibility as trust tier today
Admin — ops_admin / verification_agent
Deactivates with a mandatory reason, manages onboarding checklist.
existing scopes, extended

03Functional requirements

  • Caregiver self-service profile: bio, photo, service radius.
  • Availability schedule (day-of-week, start/end time) — informational for MVP, not yet enforced by bookings-match. Wiring availability into matching eligibility would be a real, non-trivial touch to an already-implemented and tested function; this module ships the data model and the caregiver-facing UI first, and treats matching integration as a named, deferred Phase 2+ decision rather than something decided unilaterally here.
  • Onboarding checklist (platform orientation, safety training, app walkthrough, etc.) — admin-tracked completion, informational only, does not gate trust_tier or matching eligibility for the same reason: folding it into computeTrustTier() would touch tested, existing logic for a benefit that hasn't been shown necessary yet.
  • Deactivation with a mandatory reason, logged to a history table — see § Cross-cutting for the one small, necessary touch this requires to the existing admin action that performs deactivation.

04Non-functional requirements

Profile photo storage must not block core booking flows if unset — a caregiver with no photo yet is still fully bookable, generic avatar shown.

05User flow

1
CaregiverCompletes profile (bio, photo, service radius) and sets a weekly availability pattern.
2
AdminTracks onboarding checklist completion alongside the existing verification queue.
3
FamilySees the enriched profile on the Care Team card once matched.
4
AdminDeactivates a caregiver with a required reason, which is logged, not just flipped silently.

06Information architecture

Caregiver-facing: a profile screen and an availability settings screen in caregiver_app. Admin-facing: additive tabs on the existing caregiver directory admin page — profile, availability, onboarding checklist, status history — not a new standalone page.

RLS: caregiver_profile_details/caregiver_availability — caregiver writes own, family/elder can read (same open visibility as the caregiver's existing trust tier — no consent gate, this isn't elder data), admin full access. caregiver_onboarding_checklist — caregiver reads own (transparency into what's left), only admin writes. caregiver_status_history — admin-only, in both directions; whether a caregiver should ever see their own deactivation reason is a real, unresolved fairness question flagged here rather than decided unilaterally.

08API design

No new Edge Function. Profile, availability, and checklist reads/writes are plain RLS-guarded operations. The status-history write is one additive insert added to the existing admin deactivation action — see § Cross-cutting.

09Security design

Profile photos get their own storage bucket, deliberately separate from verification documents

A profile photo is shown to any family matched to this caregiver; a government ID or police-verification document is admin-only. Sharing one bucket would risk one RLS mistake exposing the more sensitive class. A new caregiver-profile-photos bucket, following the same private-bucket-plus-signed-URL pattern as the existing verification-document storage design, keeps the two cleanly separated.

10AI architecture

Not applicable.

11Accessibility requirements

Caregiver-facing screens follow the same accessibility baseline as the rest of caregiver_app — see Module 19.

12Notification requirements

Deactivation notifies the affected caregiver (never a silent account change) via the existing notification infrastructure.

13Edge cases

  • Caregiver sets availability that's never actually checked by matching (MVP gap, stated plainly rather than implied to work) — a real ops risk if staff assume it's enforced when it isn't; worth a visible "not yet used for matching" label in the UI itself, not just this document.
  • Caregiver removes their profile photo → generic avatar fallback, no blocking.
  • Onboarding checklist incomplete but caregiver already passed BGV/police verification → they remain bookable (checklist doesn't gate eligibility, per § FR) — a deliberate, named decision, not an oversight.

14Admin dashboard requirements

Additive tabs on the existing caregiver directory page: profile view, availability view, onboarding checklist management, status history. The existing verification queue and its scope (verification_agent) are unchanged.

15Flutter project structure

apps/caregiver_app/lib/features/profile/ — profile edit, availability settings, onboarding checklist view.

16Supabase requirements

Four new tables with RLS, one new storage bucket with its own RLS policies (mirroring the existing verification-document storage pattern). No new Edge Function. One small, necessary addition to the existing admin deactivation action — see § Cross-cutting.

17Future scalability

Availability and onboarding-checklist data existing now, even unenforced, means the Phase 2+ decision to wire either into matching eligibility is a query change against data that already exists — not a fresh data-modeling exercise done under time pressure later.

Module 18 of 4 in this batch (18th overall)

Caregiver Performance & Rating System

A service-quality signal, deliberately kept separate from trust_tier. See § Overview for why conflating the two would be a mistake.

01Problem being solved

Families have no way to give feedback after a visit, and admin has no service-quality signal at all beyond credential status — which measures something different (see § Overview).

02User personas

Family member
Rates after a completed booking they requested.
write own rating
Elder
Not the primary rater for MVP — family typically manages this.
none (MVP)
Caregiver
Sees their own aggregate and review text, never the reviewer's identity.
own, anonymized
Admin
Reviews low ratings, sees full detail including rater identity.
full, ops_admin

03Functional requirements

  • Post-visit rating prompt (1–5 stars, optional short review) after a booking reaches completed.
  • One rating per booking.
  • Ratings ≤2 stars auto-flag for admin review — a low-friction, always-on quality signal rather than relying on someone to notice.
  • Caregiver sees their own aggregate and individual review text, never who wrote a given review — protects a family from any retaliation concern and is enforced at the database level, not left to client code discipline (see § Database).

04Non-functional requirements

Aggregate rating computation must stay fast as ratings accumulate — a maintained summary table, not a live aggregate query on every profile view (see § Database).

05User flow

1
FamilyBooking completes; a rating prompt appears (skippable, never blocking).
2
SystemLow ratings auto-flag; a trigger updates the caregiver's rolling summary.
3
CaregiverSees their aggregate and review text, anonymized.
4
AdminReviews flagged low ratings, with full detail, as part of ongoing quality oversight.

06Information architecture

Rating prompt on booking completion (family app); aggregate + review list on the caregiver's own profile screen (caregiver app); a low-rating review queue as an additive tab on the existing caregiver directory admin page.

07Database design

caregiver_ratingsone per bookingnew
booking_iduuid fk, unique—
caregiver_id, rated_byuuid fks—
stars, review_textint (1–5) / text, nullablereview subject to the standard never-unguarded-AI rule if ever summarized
flagged_for_review, admin_reviewedbooleanflagged_for_review auto-set true when stars <= 2
caregiver_rating_summarymaintained by trigger, not a live aggregatenew
caregiver_iduuid pk—
average_stars, rating_count, updated_atnumeric / int / timestamptzrecomputed by an AFTER INSERT trigger on caregiver_ratings — same cross-cutting-invariant-belongs-in-a-trigger pattern as the stock-decrement trigger (Batch 2) and the must-deliver trigger (Batch 3)

Anonymity toward the caregiver is enforced by a database view, not client-side omission

RLS grants row access; it does not hide individual columns from an otherwise-visible row. The caregiver-facing read path uses a dedicated view, caregiver_ratings_anonymized, that selects every column except rated_by — so the reviewer's identity is structurally absent from what a caregiver's client can ever receive, not just conventionally hidden by an app that could have a bug.

RLS on caregiver_ratings: insert requires rated_by = auth.uid() and that the caller requested the referenced booking (reusing the existing booking-visibility shape); admin full select; caregiver select is routed through the anonymized view above, not the base table directly.

08API design

No new Edge Function. Rating submission is a plain RLS-guarded insert; the summary update is trigger-driven, not application code.

09Security design

This module's access model is not the elder-consent (has_consent()) system — a rating is the caregiver's data, gated by who's allowed to rate (the requesting family member) and who's allowed to see what (admin fully, caregiver anonymized), a conceptually different actor and a different access model, named explicitly so the two aren't confused.

10AI architecture

Not required. review_text is subject to the standing never-unguarded-AI rule if any future module summarizes it.

11Accessibility requirements

Star rating input must have a non-visual equivalent (e.g. a labeled 1–5 selector, not color/shape-only stars) for screen-reader users.

12Notification requirements

None new — the rating prompt appears in-flow on booking completion, not as a separate push.

13Edge cases

  • Rating attempted twice for the same booking → blocked by unique(booking_id).
  • Family declines to rate → no penalty anywhere in the system; rating is always optional.
  • Caregiver disputes an unfair low rating → flagged_for_review/admin_reviewed support an admin-mediated review; a fuller appeal workflow is not built for MVP, named as a gap rather than solved.

14Admin dashboard requirements

A low-rating review queue, additive to the existing caregiver directory page, in the same spirit as the existing verification queue.

15Flutter project structure

apps/family_elder_app/lib/features/ratings/ — rating prompt. apps/caregiver_app/lib/features/ratings/ — aggregate + anonymized review list.

16Supabase requirements

Two new tables, one new view, one new trigger. No new Edge Function, no new consent category (not consent-model data at all, per § Security).

17Future scalability

The summary-table-plus-trigger design keeps aggregate reads O(1) regardless of how many ratings a long-tenured caregiver accumulates.

Module 19 of 4 in this batch (19th overall)

Accessibility Module

Every module from Batch 1 onward has assumed this system exists. It's specified here for the first time, and the earlier assumptions are named as exactly that — assumptions, now made real.

01Problem being solved

"WCAG 2.1 AA baseline" and "elder-mode large touch targets" have been referenced in nearly every module's Accessibility Requirements section so far, pointing at a system that didn't yet exist as anything concrete — this module is that system.

02User personas

Elder
Primary beneficiary — simple mode on by default.
own + family-editable
Family member
Can configure on the elder's behalf; has their own, separate preferences too.
own + linked elder's
Caregiver
Same underlying preference system, own record.
own
Admin
None new.
none

03Functional requirements

  • App-wide text scale: a small set of presets (default / large / extra large), not a free slider — simpler choice architecture for low digital literacy than infinite fine control.
  • High-contrast theme toggle.
  • "Simple mode" for elder-mode home — formalizes the existing three/four-action elder home screen (Part 3, extended by Batch 1's check-in button) as a configurable system property rather than a one-off screen design.
  • Elder role defaults to simple mode + large text automatically, with no settings screen required to become accessible on first use.
  • A linked family member can configure these settings on the elder's behalf — many elders will never open a settings screen themselves, mirroring the existing pattern of family acting for the elder on medications and check-ins.

04Non-functional requirements

A retroactive audit obligation, named honestly

Every "accessibility requirements" section written in Batches 1–4 assumed this system's existence. Those screens were specified, not built — but once this module's concrete settings exist, revisiting each one to actually wire them in is real follow-up work this document creates, not a change to what was already written.

05User flow

1
Elder, first useSimple mode and large text are already on — no configuration required.
2
FamilyCan adjust these on the elder's behalf from their own app.
3
Any userCan independently set their own text scale / contrast preference.

06Information architecture

A single accessibility settings screen, present in both consumer apps, reachable from the elder's profile (editable by the elder or a linked family member) and from each user's own settings.

07Database design

accessibility_preferencesone row per usernew
user_iduuid fk, unique—
text_scaletextdefault / large / extra_large
high_contrast, simple_modebooleansimple_mode defaults true for the elder role specifically

RLS: user_id = auth.uid(), plus is_linked_family(elder_id) for write access when the target user is an elder — reusing the existing helper function, not a new access primitive.

08API design

No new Edge Function — plain RLS-guarded read/write, applied client-side as a theme/layout setting.

09Security design

No new sensitivity — a user's own display preferences carry no elder-health-data weight.

10AI architecture

Not applicable.

11Accessibility requirements

This module is the accessibility requirements baseline every other module in this plan points back to — see § Overview.

12Notification requirements

None.

13Edge cases

  • Family sets a preference the elder later wants to override themselves → the elder's own edit always takes precedence in the moment; no lock preventing an elder from changing their own settings.
  • New elder account, no preference row yet → defaults apply from role alone, no blocking first-run wizard required.

14Admin dashboard requirements

None.

15Flutter project structure

packages/setu_core/design/ extended with the text-scale/contrast token system — genuinely shared, not per-app, since both consumer apps must respect the same preferences.

16Supabase requirements

One new table with RLS reusing the existing is_linked_family() helper. No new Edge Function, no new consent category.

17Future scalability

A token-based design system (rather than screen-by-screen hardcoded sizing) means future modules inherit accessibility compliance by using the shared tokens, rather than needing their own audit each time.

Module 20 of 4 in this batch (20th overall)

Multi-language Support

The data model (preferred_language, primary_language) and the Flutter l10n scaffolding already exist — this module is what completes and formalizes coverage, not what invents the system from nothing.

01Problem being solved

profiles.preferred_language and elder_profiles.primary_language already drive AI and (per PRD Part 2) UI locale, and ai-translate already exists. What's missing: an in-app language switcher, honest coverage tracking (only English/Hindi/Telugu are drafted today, per the existing project README, and unreviewed by native speakers), and a graceful fallback so an incomplete language never shows a raw translation key mid-sentence.

02User personas

Elder
Selects/uses their primary language throughout.
own preference
Family member
Own preference, independent of the elder's.
own preference
Caregiver
Own preference.
own preference
Admin / translator
Reviews machine-drafted strings before they ship as final.
new, narrow role

03Functional requirements

  • In-app language switcher in both consumer apps, backed by the existing preferred_language field.
  • Missing translation falls back to English gracefully — never a raw key like booking.confirm_cta shown to a user.
  • AI-drafted translations for new UI strings, reusing the existing ai-translate function or an equivalent approach, always marked "machine-drafted, needs native-speaker review" and never shipped as final without human review — a real quality and trust requirement for a platform serving elderly users in their own language, where a wrong or awkward translation is worse than English shown honestly.

04Non-functional requirements

Switching language must not require an app restart or lose in-progress state.

05User flow

1
UserOpens language settings, picks from the supported list.
2
AppRe-renders in the chosen language immediately; any missing string falls back to English silently, never a broken key.
3
Translator/adminReviews machine-drafted strings for a given language, marking each human-reviewed before it's considered complete.

06Information architecture

A language settings screen in both consumer apps. An optional coverage-visibility view for ops (see § Database).

07Database design

A coverage-tracking table is optional, and honestly, may be the wrong tool

A translation_coverage(language_code, string_key, status) table is possible, but every UI string × 10 languages is a lot of bespoke rows for something a third-party localization platform (Lokalise, Phrase, or similar) already does well. Flagged as optional in-platform tooling, not a requirement — the simpler path of managing coverage in Flutter's own ARB files plus an external tool is equally valid and likely less to maintain.

No required schema changes — preferred_language/primary_language already exist and already do their job.

08API design

No new Edge Function required for the switcher itself. Generating machine-draft translations for new strings can reuse the existing ai-translate function as a translator's tool, not a new AI surface.

09Security design

No new sensitivity — language preference is not elder health data.

10AI architecture

Reuses the existing ai-translate guardrail path exactly — no new AI architecture introduced by this module.

11Accessibility requirements

Directly complements Module 19 — a family member managing an elder's accessibility settings should be able to set language at the same time, in the same settings surface, not a separate disconnected flow.

12Notification requirements

Push/SMS notification content should respect the recipient's preferred_language where a translation exists — an application-level requirement on every module that sends a notification, not new infrastructure.

13Edge cases

  • Elder changes primary language after AI content was already generated in the old one → historical content is not retroactively re-translated; only new content uses the updated language.
  • A language with zero human-reviewed strings → the app functions fully in English fallback rather than being half-broken in a thin, unreviewed translation.

14Admin dashboard requirements

A coverage dashboard only if the optional table above is actually built; otherwise none.

15Flutter project structure

Standard Flutter l10n (ARB files), already scaffolded per the existing project structure — this module's job is completing coverage and adding the switcher UI and fallback handling, not building l10n tooling from nothing.

16Supabase requirements

None required. The optional coverage table, if built, is the only new schema surface.

17Future scalability

Reusing ai-translate for draft generation means adding a new supported language is a translation-review workload, not a new engineering integration.
