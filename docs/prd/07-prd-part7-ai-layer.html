Missing Modules, Batch 4: AI Layer

Part 7 of the Project Setu PRD, fourth of seven batches, and the one that needed the most restraint. PRD Part 2 §14 already locked five governing principles for AI on this platform — fixed toolset, output guardrail, mandatory disclaimers, full logging, escalation over silence — before either existing AI function (ai-visit-summary, ai-translate) was built. Every module below is designed against those five principles, not a fresh safety model invented per feature. Where a module's natural shape would have pushed toward more AI involvement than necessary, that tension is named explicitly rather than resolved by simply adding more guardrail on top.

Batch overview

The one rule every module below had to survive

"AI must never diagnose, prescribe, or replace a healthcare professional" is easy to write and easy to violate by accident three modules later, once each module is designed in isolation and the accumulated surface area is never looked at together. So it's stated once here, and every module's own AI Architecture section states specifically how that module satisfies it — not by reference back to this paragraph, but by naming its own actual mechanism.

A pattern repeated four times in this batch: AI proposes, deterministic code or a human decides

AI Care Assistant never executes a booking directly — it prepares a draft a human confirms. AI Recommendation Engine's suggestions are generated by deterministic rules over structured data, with AI (if used at all) limited to phrasing already-decided text. AI Visit Reports summarizes only content that already passed the guardrail once, never raw clinical text. Voice Assistant makes no independent content decisions — it's a modality converter feeding into the other three's already-guardrailed paths. None of these are coincidence; each is the direct consequence of applying the same question to a different shape of feature: where exactly does generative AI touch a decision that matters, and can that surface be made smaller?

Module 13 of 4 in this batch (13th overall)

AI Care Assistant

A conversational front end over data the family or elder could already see via existing screens — never a new access path, never a new source of truth.

01Problem being solved

Family and elder want to ask questions in plain language — "when's the next visit," "what medications are due today," "book me a nurse for tomorrow" — instead of navigating multiple screens. PRD Part 2 §14 already anticipated this exact shape of feature, naming get_appointment_details and get_medication_list as illustrative fixed tools before this module existed — this spec is realizing that anticipated design, not inventing new scope.

02User personas

Family member
Primary — asks questions, confirms proposed bookings.
tool calls run under their own RLS
Elder
Same conversational surface, voice-first via Module 16.
tool calls run under their own RLS
Caregiver
Out of scope for this module — a caregiver-facing assistant, if ever built, is a separate module.
none
Admin
Reviews flagged interactions via the existing AI review queue.
existing surface, unchanged

03Functional requirements

  • Conversational Q&A over a fixed, enumerated toolset: get_upcoming_bookings, get_medication_list, get_appointment_details, get_care_team_info, get_recent_timeline, get_consent_status, initiate_booking. No freeform browsing or code execution — the model can only call these named functions.
  • Every tool call executes as the requesting user, RLS-scoped — the assistant is a natural-language front end over already-secured data access, never a new one. This is the single most important design decision in this module (see § Security).
  • initiate_booking never submits a real booking directly — it prepares a draft the family must explicitly confirm via a UI card before bookings-create is actually called. AI proposes; a human commits anything with a cost.
  • Any question shaped like a medical question ("should I increase the dose," "does this mean X") gets a fixed, non-negotiable refusal directing to the assigned clinician — Part 2 §14's "escalation, not silence" principle, reused verbatim.
  • get_care_team_info never returns a caregiver's phone number, matching the existing no-direct-contact convention from the Family Dashboard (Batch 1).

04Non-functional requirements

  • Every factual claim in a response must be traceable to a specific tool call's returned data — no answer may include information no tool call actually returned.
  • Latency budget consistent with the existing ai-visit-summary/ai-translate functions.

05User flow

1
UserOpens the chat, asks a question or taps a suggested-question chip.
2
ModelSelects an appropriate tool from the fixed set.
3
Tool executesAs an RLS-scoped query under the requesting user's own session — never the service-role client.
4
Model composes an answerFrom only the data the tool returned.
5
GuardrailSame two-layer check as every other AI output; flagged responses are held for review, never delivered.

06Information architecture

A chat screen reachable from main nav, with suggested-question chips on first open so a first-time user isn't staring at a blank box wondering what's allowed.

07Database design

No new tables. One additive value on the existing ai_interaction_type enum — see § Cross-cutting.

08API design

POST/ai/care-assistant
New Edge Function, following the existing ai-visit-summary/ai-translate shape: requireUser(), fixed system prompt, OpenAI function-calling restricted to the fixed toolset. The one deliberate deviation from its siblings: tool-call execution uses a Supabase client built from the requesting user's own JWT, not the service-role admin client the other two AI functions use for their writes — see § Supabase for the new shared helper this requires.

09Security design

RLS-scoped tool execution is the module's core safety property

Every other Edge Function in this codebase uses the service-role client plus manual, hand-written re-checks of the exact authorization it needs. That pattern would be actively wrong here: an LLM's tool selection is not a fixed, enumerable set of call sites the way a REST endpoint's logic is — hand-re-implementing every consent check the model might trigger, correctly, for every tool, would be far more error-prone than letting Postgres RLS (already exhaustively tested by every other module) do it. So this function is deliberately the one place in the codebase where an Edge Function executes a query as the caller, not as the service role.

Consent-denied is not the same as empty, and the assistant must say so

If get_medication_list returns nothing because RLS denied the caller (no medication_list consent) versus because the elder genuinely has no medications, those are different facts with different implications. The assistant must distinguish "I don't have access to that — you may need to request it" from "there's nothing here" — collapsing the two would produce a false and potentially dangerous "they're on no medications" answer.

10AI architecture

Two layers on the input side (beyond the existing single output guardrail every other AI function has): a fast pattern pre-filter refuses obviously medical-shaped questions before an API call is even made, and the existing output guardrail catches anything that slips through indirectly. This is a genuine escalation beyond ai-visit-summary's single-output-guardrail design, justified because this module responds to arbitrary user phrasing rather than processing one specific, known input.

11Accessibility requirements

Text chat is the baseline; voice input/output is Module 16's responsibility layered on top, not rebuilt here — see that module's own scope statement.

12Notification requirements

None generated directly by this module.

13Edge cases

  • Out-of-scope question (weather, general knowledge) → fixed refusal naming what the assistant can actually help with.
  • A request needing a tool that doesn't exist yet → honest "I can't do that yet, here's how to do it manually," never a fabricated answer.
  • Consent-denied vs. genuinely-empty data → handled distinctly, see § Security.

14Admin dashboard requirements

None new — flagged interactions surface in the existing AI review queue, which already powers exactly this workflow for the other two AI functions.

15Flutter project structure

apps/family_elder_app/lib/features/care_assistant/ — ChatScreen, SuggestedQuestionChips, BookingConfirmationCard (the human-confirms-before-commit UI for initiate_booking).

16Supabase requirements

One new Edge Function (ai-care-assistant). One additive value on ai_interaction_type (care_assistant_chat — see § Cross-cutting). One new _shared helper for constructing an RLS-scoped ("as user") Supabase client inside an Edge Function — a genuinely new pattern in supabase/functions/_shared/, additive alongside the existing supabaseAdmin()/requireUser() exports, not a change to either of them. No new tables, no new storage.

17Future scalability

The fixed toolset is deliberately extensible: any future module can register a new tool function without touching the guardrail architecture — once Care Plans (Batch 6) exists, a get_care_plan_details tool slots in the same way these seven do.

Module 14 of 4 in this batch (14th overall)

AI Visit Reports

A periodic rollup across many visits — distinct from the existing ai-visit-summary, which handles one visit's raw notes. This module never touches raw caregiver text at all.

01Problem being solved

ai-visit-summary already turns one caregiver's raw notes into one plain-language summary per visit. Family additionally wants the trend view — "how did this month go overall" — which no single-visit function can answer, and which naively built might mean reprocessing a month of raw clinical text through a second, parallel AI pathway.

02User personas

Family member
Receives periodic reports, consent-gated per section.
read, consent-scoped
Elder
Full unfiltered view of their own reports.
read, own record
Caregiver
Not a recipient or generator beyond their existing per-visit notes.
none new
Admin
Reviews flagged reports via the existing queue.
existing surface

03Functional requirements

  • Family-configurable period (weekly or monthly).
  • Aggregates: visit count/completion rate, medication adherence % (Batch 2), check-in consistency (Batch 1), notable Timeline events (Batch 1) — and only already-guardrailed, already-delivered text (prior ai_interactions.output_text entries that were not flagged), never raw caregiver notes directly.
  • Delivered as a periodic card/notification, not generated on demand mid-conversation.

04Non-functional requirements

Generation must not block or slow any real-time path — it is a scheduled batch job, not a request-time operation.

05User flow

1

2

3
GuardrailSame two-layer check, applied as defense in depth even though the input was already safe once.
4

A periodic report list/detail screen, reachable from the Family Dashboard (Batch 1).

08API design

POST/ai/visit-reports-generate
New scheduled Edge Function, n8n-triggered (same external-schedule pattern as payouts-run, checkins-escalation-sweep). Aggregates the period's data, calls the model with a report-specific fixed system prompt, runs the existing guardrail, writes ai_visit_reports and logs to ai_interactions under a new type — see § Cross-cutting.

09Security design

This module's core safety architecture is what it refuses to read

By aggregating only structured metrics and content that already passed the guardrail once, this module never introduces a new raw-clinical-text processing pathway. The guardrail on the composed report is defense in depth, not the primary control — the primary control is the input scoping itself.

10AI architecture

Same two-layer guardrail as every other AI output, plus the mandatory disclaimer, plus full ai_interactions logging — no exceptions or shortcuts for this module despite its pre-sanitized input.

11Accessibility requirements

Same baseline as the rest of the family-facing surface.

12Notification requirements

Delivered via the existing notification infrastructure (Batch 3) as a new notification_types entry, not a bespoke delivery path.

13Edge cases

  • Zero activity in the period → the report says so plainly, never padded or invented content to fill space.
  • Insufficient consent for a full picture → a partial report explicitly names which sections are unavailable due to missing consent, same transparency principle as Module 13's consent-denied handling.

14Admin dashboard requirements

None new — flagged reports use the existing AI review queue.

15Flutter project structure

apps/family_elder_app/lib/features/visit_reports/.

16Supabase requirements

One new table (ai_visit_reports), one new scheduled Edge Function, one additive ai_interaction_type value (periodic_report).

17Future scalability

Aggregation-of-pre-approved-content keeps this module's cost and risk profile flat as visit volume grows — it never needs to re-read raw text regardless of how many visits occurred in a period.

Module 15 of 4 in this batch (15th overall)

AI Recommendation Engine

The highest-risk name in this entire 25-module plan for scope creep toward clinical recommendation. Scoped hard, twice, on purpose.

01Problem being solved

Family would benefit from proactive, gentle, operational suggestions surfaced from patterns in the data — never health or clinical recommendations, full stop, restated here as the first sentence of this module specifically because "recommendation engine" as a name invites exactly that scope creep if nobody says so explicitly before the database design starts.

02User personas

Family member
Receives, dismisses, or mutes suggestions.
consent-scoped
Elder
Same, own record.
consent-scoped, own
Caregiver
Not a recipient.
none
Admin
Suggestion-generation health/accuracy visibility, feeding Batch 6's Care Analytics Dashboard.
read-only, cross-referenced

03Functional requirements

  • A closed, enumerated set of suggestion types — never an open-ended "the model decides what to suggest": schedule-gap ("no companion visit booked in 14 days"), adherence-pattern ("check-in or medication adherence trending down — worth a conversation," never a diagnosis), refill-timing (a smarter version of Medicine Refill Management's threshold alert, factoring in pause windows), care-team-continuity ("your preferred caregiver has been unavailable — consider a backup preference").
  • Every suggestion is traceable to the specific data pattern that triggered it — logged alongside the suggestion, so the system is explainable and auditable, never a black box.
  • Dismiss/mute per suggestion type, reusing notification_preferences (Batch 3) rather than a parallel preference system.

04Non-functional requirements

Suggestion volume rate-limited per elder (a maximum number pending at once) — unlimited suggestions would undermine trust in the feature exactly the way notification fatigue does elsewhere in this plan.

05User flow

1
SystemPeriodic sweep evaluates the closed set of deterministic pattern rules over structured data.
2
A rule firesA suggestion is generated, its triggering metric recorded.
3
FamilySees the suggestion, can act, dismiss, or mute that type going forward.

06Information architecture

Suggestion cards on the Family Dashboard (Batch 1); a mute/preferences surface shared with Family Notification Center (Batch 3).

07Database design

care_suggestionsclosed suggestion_type set, always explainablenew
elder_id, suggestion_typeuuid fk / textclosed, enumerated set — see § FR
trigger_metricjsonbthe specific data point(s) that fired the rule — mandatory, for auditability
suggestion_text, statustext / enumstatus: pending / dismissed / acted_on

RLS reuses the same consent-mapping-by-source approach as reminders (Batch 2): visibility depends on which category the specific suggestion_type implies (a medication-related suggestion needs medication_list consent, a schedule-gap suggestion needs visit_history), via the same kind of small mapping helper rather than a single static policy.

08API design

POST/care-suggestions/generate
New scheduled Edge Function (weekly). Evaluates the closed set of rules — mostly deterministic threshold logic over structured data, not a model call. An LLM is optionally used only to phrase an already-decided suggestion's text naturally; it is never involved in deciding whether or what to suggest. See § AI Architecture.

09Security design

No new sensitivity class — every underlying data point already has a consent category from an earlier batch; this module only reads and pattern-matches, writing nothing back to source tables.

10AI architecture

The primary safety control is that this is a rules engine, not a language model deciding outcomes

Most suggestion types require zero generative AI — "no visit booked in 14 days" is a plain SQL condition. Where natural-language phrasing is desired, an LLM may be used only to word an already-determined, already-safe suggestion, and that output still passes the same two-layer guardrail as everything else, as defense in depth on top of the real control. Stating this hierarchy explicitly — deterministic rules first, guardrail second, never the reverse — is this module's entire answer to "how does this never become a diagnosis engine."

11Accessibility requirements

Suggestion cards use the same plain-language, non-alarming tone discipline established for Daily Check-ins and Smart Reminder System.

12Notification requirements

Delivered through the existing notification infrastructure; preferences reuse notification_preferences directly rather than a parallel system.

13Edge cases

  • A suggestion goes stale before being seen (e.g. "book a visit" but family already booked one independently) → the sweep re-checks current state before surfacing, same stale-check principle as Smart Reminder System (Batch 2).
  • Suggestion volume exceeds the per-elder cap → lowest-priority pending suggestions are superseded, not stacked indefinitely.

14Admin dashboard requirements

Suggestion accuracy/dismissal-rate visibility, feeding Care Analytics Dashboard (Batch 6) rather than a standalone admin page.

15Flutter project structure

apps/family_elder_app/lib/features/suggestions/ — SuggestionCard, dismiss/mute actions reusing Module 9's preference UI patterns.

16Supabase requirements

One new table (care_suggestions) with consent-mapped RLS. One new scheduled Edge Function, predominantly deterministic with an optional, narrowly-scoped LLM phrasing step. No new consent category — reuses existing ones per suggestion_type.

17Future scalability

New suggestion types are additive entries to the closed set, each requiring an explicit, reviewable rule — the enumerated-set design is what keeps this module auditable as it grows, rather than an ever-more-autonomous model making an ever-larger range of judgment calls.

Module 16 of 4 in this batch (16th overall)

Voice Assistant

A modality converter, not a second AI surface — transcribed speech routes into the already-guardrailed paths Module 13 and Batch 1's Daily Check-ins already own.

01Problem being solved

Elders with low digital literacy or vision/dexterity limitations benefit from voice as an alternative to tapping and reading. Daily Check-ins (Batch 1) already anticipated this — its source field included voice_assistant before this module was specified.

02User personas

Elder
Primary — voice check-in, voice questions to the Care Assistant.
elder-mode only
Family member
Not the primary target; voice is an elder-mode accessibility feature.
none (MVP)
Caregiver
Not applicable.
none
Admin
None new.
none

03Functional requirements

  • Speech-to-text routed to a fixed set of recognized intents: daily check-in, a Care Assistant question, a small set of navigation commands — never a general voice-command-anything system, mirroring the fixed-toolset philosophy of Module 13.
  • Text-to-speech for reading back responses, reminders, and confirmations.
  • Push-to-talk only for MVP — explicitly no always-listening wake-word service. An always-listening microphone in an elder's home is a real privacy exposure disproportionate to what this module needs to deliver; stated as a deliberate constraint, not a missing feature.

04Non-functional requirements

  • Must tolerate regional accents and, later, multiple languages (cross-ref Multi-language Support, Batch 5).
  • Graceful offline/unreachable fallback: degrade to tap-based interaction, never a dead end.

05User flow

1
ElderTaps a mic button (explicit press, never passive listening).
2
Speech-to-textTranscribes, matches against the fixed intent set.
3
RoutedInto the matching existing flow — check-in or Care Assistant — which applies its own, already-specified guardrail.
4
Text-to-speechReads the response back.

06Information architecture

A mic button on the elder-mode home screen and within the Care Assistant chat screen — both additive UI elements on existing screens.

07Database design

No new tables. Voice is an input/output modality over existing flows; the daily_checkins.source field already anticipated it correctly in Batch 1.

08API design

Platform-native speech APIs first, a server-side function only if proven necessary

Android/iOS both ship built-in speech recognition and text-to-speech with no backend call, no new secret, and no added latency hop. That should be evaluated first. A server-side voice-transcribe Edge Function (needed only if a third-party STT/TTS provider proves necessary for target-accent/language quality) is the fallback, not the default — an honest trade-off named here rather than assuming a cloud API is required before anyone has checked whether the device's own capability is good enough.

09Security design

If a server-side provider is ever used, its key is Edge-Function-owned per the standing "secrets never reach the client" rule. Voice recordings, if temporarily held for transcription, must not persist beyond that single request — a voice sample is itself biometric-identifying, a materially different privacy consideration than typed text, and no permanent audio storage is in scope without a separate, explicit consent decision this module does not make on its own.

10AI architecture

This module makes no independent content decisions. Transcribed text is handed to whichever existing, already-scoped function it was routed to; the guardrail that applies is that destination's, not a new one built here. Keeping voice as a pure modality converter — rather than a second AI surface with its own safety model to maintain — is the deliberate scoping choice.

11Accessibility requirements

This module is the platform's voice-accessibility pillar. Batch 5's Accessibility Module owns the overall visual/interaction system (text scale, contrast, simplified navigation); this module owns speech specifically — the same precise division-of-labor pattern used for Reminders/Notifications (Batches 2–3) and Care Assistant/Voice here, stated once more for consistency across the plan.

12Notification requirements

Reminders can optionally be read aloud via text-to-speech — an enhancement to Smart Reminder System's existing delivery, not a new notification type.

13Edge cases

  • Background noise or unclear speech → graceful "I didn't catch that — try again or tap instead," never a misrouted action.
  • Request outside the fixed intent set → the same honest fallback Module 13 uses for out-of-scope questions.

14Admin dashboard requirements

None new for MVP.

15Flutter project structure

apps/family_elder_app/lib/features/voice/ (elder-mode only) — MicButton, VoiceFeedbackOverlay; a shared intent-router in setu_core if reused between the check-in and Care Assistant entry points.

16Supabase requirements

No new tables. No new consent category — voice is a modality, not a new data category (persistent audio storage, if ever added, would need its own separate consent treatment, explicitly out of scope here). Possibly one new Edge Function (voice-transcribe), only if platform-native STT/TTS proves insufficient.

17Future scalability

The platform-native-first approach scales at zero marginal server cost; the trigger for adding server-side infrastructure is a specific, demonstrated accent/language gap platform capability can't cover — not a default assumption made now.

Cross-cutting

Every touch to an existing, already-implemented module

Three additive values on one existing enum, and nothing else:

Existing moduleWhat's addedWhy it's necessary
ai_interaction_type enum (on ai_interactions, PRD Part 2 §11)Three new values: care_assistant_chat, periodic_report, suggestion_phrasingThe existing four values (visit_summary, translation, reminder, scheduling_assist) don't describe these three new interaction shapes precisely enough for meaningful audit/QA — conflating them into an existing value would blur exactly what happened in a given interaction, which defeats the point of the column.

No existing Edge Function's logic is modified. No existing table beyond this one enum is touched. The new "as-user" Supabase client helper for Module 13 is purely additive to _shared/, alongside — not instead of — the existing supabaseAdmin().
