10 — Information Architecture

Three surfaces, one trust graph

A single do-everything Flutter app would force compromises on both ends: an elder who wants three big buttons and voice input, and a family member who wants a dense dashboard, don't belong on the same screen. Recommendation: three surfaces sharing one backend and one data model.

Flutter · consumer

Family & Elder App

One codebase, two experience modes selected at login by role. Family mode: full dashboard, booking, consent management. Elder mode: large-text, voice-first, three-action home screen (Call for Help, Book Help, Today's Visit) — deliberately not a shrunken version of the family UI.

Flutter · caregiver

Caregiver App

Separate app, separate build. Job queue, accept/decline, navigation, OTP start/end scan, earnings and payout status. Different enough in job (dispatch, not care management) that bundling it into the consumer app would bloat both.

Web · internal

Admin / Ops Dashboard

Not Flutter — a web app. Ops staff work at desks with dense tables, bulk actions, and real-time SOS monitoring; that's a desktop-web job, not a mobile one. Detailed in Section 16.

Underneath all three: one Supabase project, one Postgres schema, one consent graph. An elder's data has exactly one source of truth regardless of which surface reads or writes it — the alternative (per-surface caches or duplicated models) is how consent violations happen by accident.

12 — API Design

Two layers: RLS-guarded direct access, and Edge Functions for anything with a secret or a rule

Supabase's client SDK can talk to Postgres directly for simple, already-permission-scoped reads (a family member's own booking history, an elder's own profile) — Postgres Row Level Security enforces the boundary, no custom API needed. Anything that (a) touches a third-party secret, (b) enforces a business rule beyond "is this my row," or (c) needs to be atomic across tables goes through a Supabase Edge Function instead.

GET/regions/:code/config
Returns the active region's currency, tax profile, payment/BGV provider, and compliance profile — clients read this once at startup rather than hardcoding India/INR anywhere.
POST/bookings
Validates required trust tier for the requested service before allowing a match — never left to the client.
POST/bookings/:id/match
Caregiver-matching: filters by trust tier, location, language, availability.
POST/bookings/:id/otp/start
Generates + verifies visit-start OTP; flips status to in_progress.
POST/bookings/:id/otp/end
Verifies visit-end OTP; triggers payout scheduling.
POST/payments/create-order
Server-side Razorpay order creation — API key never touches the Flutter client.
POST/payments/webhook
Razorpay webhook receiver; verifies signature before writing to payments.
POST/payouts/run
Triggered by n8n on schedule; batches RazorpayX payouts for completed, unpaid bookings.
POST/sos/trigger
Writes sos_event, fans out to family + on-call ops + nearest responder in parallel; the 108-first screen is enforced client-side and logged server-side via ack_108_shown_at.
POST/ai/visit-summary
Scoped OpenAI call (Section 14); writes to ai_interactions before returning to the client.
POST/verification/idfy-webhook
Receives BGV status callbacks, updates caregivers.bgv_status and recomputes trust_tier.
GET/me/data-export
DPDP data-portability right — full export of a data principal's own records.
POST/me/erasure-request
DPDP erasure right, subject to legal/audit retention exceptions (flagged, not deleted immediately).
13 — Security Architecture

RLS is the enforcement layer, not a formality

RBAC via Supabase custom claims

JWT carries role (elder / family_member / caregiver / admin) plus linked ids. Every RLS policy reads these claims — there is no code path where a client can read another elder's data because the Flutter app "just didn't show it."

Consent-gated policies, not table-level policies

Tables like bookings.health_notes or location fields aren't gated by a simple "is family member" check — the RLS policy calls a Postgres function has_consent(elder_id, requesting_user, category) that checks consent_grants at query time. Revoking consent takes effect on the next query, not on the next deploy.

Column-level encryption for the highest-sensitivity fields

Government ID numbers and raw medical notes are encrypted at the column level (pgsodium/pgcrypto) in addition to Supabase's at-rest encryption — so a database dump or misconfigured policy doesn't expose them in plaintext.

Secrets live in Edge Functions, never in the client

OpenAI, Razorpay, RazorpayX, and IDfy keys are Edge Function environment variables only. The Flutter apps never hold a third-party API key.

Guardian-override consent needs a real workflow, not a checkbox

consent_grants.granted_via = documented_guardian_process exists for the genuine edge case of an elder who lacks capacity to consent (e.g. advanced dementia) — but it must require admin review and a documented basis (medical certification, power of attorney), logged and auditable, never a self-serve toggle a family member flips unilaterally. Flagging this as a Part 3 legal/ops workflow to design properly, not a database default.

Caregiver app device & session security

Short-lived access tokens with refresh rotation; location sharing scoped to active-booking windows only, not always-on background tracking of caregivers between jobs.

DPDP operational readiness

Breach detection + a 72-hour reporting runbook, a named DPO contact point, and DPIA documentation for the consent/location/health data flows — procedural detail belongs in Part 3, but the schema and RLS design above are already built to make these possible rather than retrofitted.

14 — AI Architecture

Constrained by design, not by prompt wording alone

"Don't diagnose" is not something an LLM reliably self-enforces through instructions alone. The architecture below treats it as a system constraint with multiple independent layers, so that a single weak point doesn't become the only line of defense.

1
Fixed toolset, no freeform capabilityEach interaction_type (visit_summary, translation, reminder, scheduling_assist) has its own scoped system prompt and its own fixed set of callable functions — e.g. get_appointment_details, get_medication_list, translate_text. The model cannot browse, execute code, or answer outside its assigned task.
2
Output guardrail before the user ever sees itEvery response passes a lightweight classifier (rule-based pattern matching for dosage/diagnosis-shaped language, plus a cheap moderation-model pass) before being returned. A flagged output is held for human review rather than delivered.
3
Mandatory disclaimers on health-adjacent outputAny visit summary or reminder touching medication or symptoms is appended with a standard, non-negotiable disclaimer and a "confirm with your clinician" pointer — not left to the model's discretion.
4
Full logging for audit and QAEvery interaction, flagged or not, is written to ai_interactions — both for the DPDP audit trail and so QA can sample real outputs and tighten the guardrail over time.
5
Escalation, not silence, on ambiguityIf a family member asks the AI something that reads as a medical question ("should I increase the dose?"), the correct behavior is routing to a human (the assigned nurse or the family's own doctor), never an AI-generated answer, even a hedged one.
15 — Backend Architecture

How the pieces fit

Supabase (Postgres + Auth + Storage + Realtime) is the system of record and handles simple RLS-guarded reads directly from the Flutter clients. Edge Functions (Deno, colocated with the database) own every path that touches a secret or a cross-table rule — bookings, payments, payouts, SOS, AI, verification webhooks. n8n is the scheduler/orchestrator, not a business-logic owner: it triggers Edge Functions on a timer or webhook (nightly payout batch, appointment-reminder sweep, polling IDfy/police-verification status) rather than embedding logic of its own, so the actual rules live in one place. FCM delivers push (bookings, SOS, reminders); Supabase Realtime pushes live updates to the admin dashboard's SOS monitor. PostHog tracks product analytics — event payloads use anonymized/categorical properties only (e.g. service_category, not free-text health content), so analytics can't become a second, unaudited copy of sensitive data.

Payment provider is an interface, not a direct call

Every Edge Function that touches payments calls an internal PaymentProvider port (create_order, capture, payout, refund) resolved by the caller's region_id → payment_provider. Razorpay/RazorpayX is the only adapter implemented at MVP. Phase 5's NRI international-card payments still route through Razorpay's international-card support with no interface change. Phase 6 country-specific gateways (e.g. Stripe for the US/UK/EU) are a new adapter behind the same port, not a rewrite of every call site.

Single region deployment at MVP, sharding is a Phase 6 concern — not before

Phases 1-5 (Visakhapatnam through NRI family accounts) all keep the elder resident in India, so one Supabase project remains the system of record throughout — region_id partitions city/state operations logically without needing separate infrastructure. Phase 6 is the point where an elder is resident in another country, which is also the point real data-residency law (GDPR in the EU, for instance) requires a genuinely separate regional deployment. Building that split before Phase 6 needs it would be speculative infrastructure with no one to serve it — the regions table is what makes deferring it safe rather than short-sighted.
