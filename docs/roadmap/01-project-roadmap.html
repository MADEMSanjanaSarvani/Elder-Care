Project Setu — Founding CTO Brief

Build Roadmap: Problem Validation to MVP Launch

A phase-gated sequence for building a trusted, verified elder-care marketplace in India — ordered so that no phase begins before the one before it has produced what it depends on.

Category
Elder care marketplace, India
Pilot city
Visakhapatnam
Prepared
15 July 2026
Scope
Phase 1 → Phase 9, MVP only

How to read this. Each phase below is a gate, not a suggestion: it lists what has to happen, what's deliberately off-limits until later, what it can't start without, what it must produce, and the order to do the work in. A phase's Dependencies should point only at a prior phase's Deliverables — if it doesn't, the sequence is wrong and needs fixing before work starts, not after.

1

Problem Validation

Prove the problem is real, for both the elder and the family paying for care, before a single screen gets drawn.

Do now

  • Write the problem hypothesis as one falsifiable sentence, not a mission statement
  • Separate and interview two personas: the elder (care recipient) and the family payer (usually an adult child, often out-of-city) — their needs diverge, so validate them separately
  • Run 30–50 qualitative interviews in the pilot city across both personas
  • Test willingness to pay: who pays, how often, subscription vs. per-visit
  • Name the trust barrier explicitly — what it actually takes for a family to let a stranger into a parent's home — this is the category's real risk, ahead of demand
  • Teardown existing options: informal caregiver networks, nursing agencies, hospital home-care wings, other elder-care startups
  • Scan the regulatory landscape (DPDP, gig-worker classification, care-worker liability) to know the constraints exist — not to design for them yet
  • Set an explicit go / no-go bar before starting

Not yet

  • Wireframes, branding, or a name
  • Caregiver recruiting or verification
  • Technology or vendor selection
  • Final pricing — hypotheses only
  • Anything resembling a prototype

Depends on

Nothing — first phase

Produces

  • Interview synthesis across both personas
  • Two persona definitions (elder, family payer)
  • Willingness-to-pay findings
  • Competitive teardown
  • Go / no-go recommendation
Order

desk research ‖ interviews (parallel) → synthesis → go/no-go gate

2

Business Model Planning

Decide who pays, who's liable, and who the caregiver legally is — before those choices get baked into a product flow.

Do now

  • Choose and pressure-test the revenue model (commission, subscription, or hybrid) against Phase 1's willingness-to-pay data
  • Model unit economics: CAC, LTV, contribution margin per visit, caregiver payout share
  • Decide the legal posture — merchant-of-record marketplace vs. facilitator — this determines licensing, tax, and liability
  • Decide the caregiver engagement model: employee, gig/contract, or partner-agency sourcing, and its exposure under the Code on Social Security 2020
  • Set trust & safety commitments as business requirements: verification standard, insurance, SOS response SLA
  • Select and justify the pilot city
  • Define pilot success metrics before building anything
  • Build a 12–24 month financial model

Not yet

  • Screens, flows, or wireframes
  • Engineering or data modeling
  • Ops hiring beyond pilot-scale headcount
  • Multi-city planning

Depends on

3

Product Planning

Cut the MVP down to the smallest loop that proves the core promise — book, verify, visit safely, see proof of care — and freeze it.

Do now

  • Write core journeys as narratives first: elder onboarding, family onboarding, booking, visit lifecycle, emergency, payment, trust touchpoints
  • Derive a prioritized MVP feature list from those journeys, not the other way around
  • Name the non-negotiable trust minimum for MVP: verified background checks, visit-start/-end verification, SOS, consent controls — these ship on day one or the category promise is broken
  • Apply a prioritization framework (MoSCoW or RICE) to split MVP-must from later
  • Write an explicit in/out scope document and get it signed off
  • Define launch-day content needs: service catalog, pilot-region configuration, initial pricing
  • Define MVP success metrics: activation, booking completion, SOS response time, verification cycle time

Not yet

  • Visual design or UI components
  • Schema or API contracts
  • Caregiver recruiting execution
  • Any code

Depends on

Phase 2 → revenue modelPhase 2 → pilot metricsPhase 1 → journeys & personas

Produces

  • Prioritized MVP feature list
  • Written user journeys
  • Signed-off scope document (in / out)
  • MVP success metrics
Order

journeys → feature list → prioritize → scope lock (sign-off gate)

4

UI/UX Design

Design for the persona with the least patience for complexity — an elder, often with low digital literacy — and let that discipline the whole system.

Do now

  • Information architecture per surface: family/elder app, caregiver app, admin dashboard
  • Wireframes for the locked MVP journeys only
  • Accessibility-first rules for the elder persona: large touch targets, one decision per screen, high contrast, low-literacy-friendly copy
  • A minimal design system: type scale, color, spacing tokens — foundation, not a full library
  • Design the trust signals deliberately: verification badges, the SOS control, "who can see what" consent screens
  • Usability-test wireframes with real elders and real family members
  • Decide the multi-language content strategy — which languages, how switching works — at a design level

Not yet

  • Engineering environment or dev setup
  • A full post-MVP design system
  • Caregiver-app features beyond MVP
  • Motion and animation polish

Depends on

5

Technical Architecture

Decide the consent and access model as an architectural principle, not a feature — everything the platform is trusted to do rests on it.

Do now

  • Choose the stack for speed-to-MVP and team fit, not novelty
  • Model core entities conceptually: users, elder profiles, bookings, caregivers, verification records, payments, consent — relationships, not full schema yet
  • Fix the security/privacy principles up front: consent-first data access, role-based access, audit logging, a DPDP compliance approach
  • Map integration boundaries: payments, background verification, notifications, location
  • Flag the scalability seams that are cheap now and expensive later, even for a single-city launch
  • Decide build vs. buy per capability (payments processor, ID verification vendor, OTP provider)
  • Plan environments (dev / staging / prod) and a CI/CD approach
  • Keep a technical risk register: vendor lock-in, cost-at-scale, compliance exposure

Not yet

  • Writing code
  • Provisioning production infrastructure
  • API endpoints or migrations
  • Finalizing every table and field

Depends on

6

Development

Ship the whole loop thin before making any single part of it wide — a booking that goes safely end-to-end beats ten features that don't connect.

Do now

  • Set up repos, environments, and CI/CD per the Phase 5 plan
  • Build in vertical slices tied to the core value loop, not by technical layer
  • Sequence: identity & auth → elder/family profile → caregiver verification → booking → visit lifecycle → payments → SOS → consent controls → notifications
  • Hold the Phase 3 scope line — anything not in MVP goes to a tracked backlog, not into this build
  • Keep code review and documentation discipline from the first commit
  • Build the admin/ops tooling needed to actually run the pilot: verification queue, SOS monitor, booking oversight

Not yet

  • Anything explicitly deferred in the Phase 3 scope doc
  • Scaling work beyond what Phase 5 flagged as cheap now
  • Cutting the trust/safety core to hit a date

Depends on

Phase 5 → architecture decisionsPhase 4 → approved designs

Produces

  • Working MVP codebase for the locked scope
  • Admin / ops tooling
  • Technical documentation
  • A staging environment running the full flow
Order

each slice above ships demoable and testable before the next begins — no slice starts while the prior one is unverified

7

Testing

Test the consent model adversarially, not just the happy path — "who can see what" is the platform's actual trust claim.

Do now

  • Functional, end-to-end testing of every MVP journey
  • Adversarial access-control testing of the consent model — who can see what, verified by attempted bypass, not by reading the policy
  • Trust & safety scenario testing: SOS response, caregiver-verification rejection, OTP mismatch/fraud paths
  • Payment reconciliation testing: refunds, payout edge cases, webhook retries — money has to be exactly right
  • Load/performance testing sized to pilot scale, not hypothetical future scale
  • A second usability round with real elder and family users, now on the real product
  • A formal pilot-readiness go/no-go review

Not yet

  • Testing features outside MVP scope
  • Any public or marketing activity
  • Infrastructure scaling decisions beyond what testing actually shows is needed

Depends on

Phase 6 → MVP scope complete

Produces

  • Functional, security, load, and usability test results
  • Defect log with resolution status
  • Pilot-readiness go/no-go report
Order

functional → access control → trust & safety scenarios → payments → load → usability → go/no-go

8

Deployment

Go live to a limited cohort with a verified caregiver pool already in place — never a public switch-on with an empty supply side.

Do now

  • Provision production per the Phase 5 environment plan
  • Seed pilot-city data: region config, service catalog, initial pricing
  • Recruit, verify, and train the initial pilot caregiver pool — start this early enough to overlap late Development/Testing, since real bookings can't run without it
  • Set up monitoring, alerting, and an on-call plan — SOS in particular cannot have downtime
  • Write the rollback and incident-response plan before go-live, not during an incident
  • Launch as invite-only or capacity-capped in the pilot area, not a full public switch-on
  • Stand up customer support — a manual, human process is fine for MVP, but it has to exist

Not yet

  • Marketing spend or PR
  • Any multi-city rollout
  • Feature additions during deployment — freeze scope

Depends on

Phase 7 → go/no-go approval

Produces

  • Live production environment
  • Seeded pilot-city data
  • Verified initial caregiver pool
  • Monitoring & incident-response runbook
  • Soft-launch plan
Order

infra & monitoring → caregiver onboarding (overlaps earlier phases) → data seeding → soft launch → stability watch

9

MVP Launch

Launch is the start of measurement, not the finish line — hold every claim from Phase 2 up against what the pilot actually does.

Do now

  • Launch to the pilot city only, targeting the personas validated in Phase 1
  • Track launch success against the exact metrics set in Phase 2 and Phase 3 — bookings completed, repeat rate, SOS SLA, caregiver supply/demand balance, NPS from both personas
  • Review pilot health on a fixed cadence (e.g. daily) for the first 2–4 weeks
  • Feed real early-user feedback directly into backlog prioritization
  • Run a formal retrospective at the end of the pilot window: what was validated, what wasn't, what changes before scaling

Not yet

  • Any multi-city expansion decision, before the pilot metrics are reviewed
  • Caregiver hiring beyond pilot needs
  • New feature development outside urgent fixes, before the retrospective is done

Depends on

Phase 8 → stable soft launch

Produces

  • Launch report against pilot success metrics
  • User feedback synthesis
  • Go / no-go recommendation for scale-up
  • Prioritized post-MVP roadmap
Order

launch to pilot cohort → monitor against metrics → collect feedback continuously → retrospective → scale decision

Where this project actually stands against this sequence

This roadmap is written from a clean slate, as asked. In reality, this codebase already has a working MVP core — booking, matching, OTP visit verification, SOS, Razorpay payments/payouts, and DPDP data rights — live-verified against a real Supabase project, plus a full architecture for 25 further modules and one batch of that already built (Family Dashboard, Elder Care Timeline, Daily Check-ins, Family Member Management).

That work was not built in this exact phase order, and Phases 1–2 here were never run as formal, documented exercises against real interview data. If useful, the next step is a short gap review: hold the existing build against this sequence, name what Phase 1 and Phase 2 evidence is actually missing, and decide whether to backfill it before continuing forward, or treat the pilot itself as the validation. That review is a separate task — say the word and it's next.
